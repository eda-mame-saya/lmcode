## 0. 背景とスコープ

### 0.1 背景

* VS Code + Continue + Ollama が社内で不安定（ファイル読み書き失敗が多発）
* クラウド AI が常時使えるとは限らない → ローカル LLM と併用したい
* 社内から **コーディング用途の問い合わせ・機能要望が継続**している（入力中補完など）

### 0.4 成功条件（MVP）

1. プロジェクトフォルダを開き、**階層ツリー**で辿れる（除外ルール適用。第一ターゲットは Flutter）
2. チャットが **複数ファイルを読んで** 変更案を出せる
3. 中央で差分を確認し、**ファイル単位で適用／却下**できる。新規ファイルは **作成カードで人手承認**して機械作成できる
4. 手編集・ディスク保存ができる。手動のビルド等は **内蔵ターミナル**（または外部 IDE）。Flutter で Agent自動実行 ON のときは analyze と test を自動で回す（§5.4.1）
5. エラー文言貼付→**エラー解析**で素早く修正依頼できる

### 0.5 MVP 確定事項

| 項目 | 内容 |
|------|------|
| Agent 入出力 | **フェンスパース併用**（§5.5）。パッチは **Begin/End Patch** |
| 書き込みの正 | 未保存タブがあるファイルは **タブ優先**。ディスク保存は **Add の作成**／**Update の自動適用**／**選択範囲を置換**／**提案行・カーソルへの挿入** の成功時 |
| レイアウト | **共通シェルなし**（専用フルレイアウト）。サイドバーから push |
| 初回 OS | **macOS のみ提供**（サイドバー入口・`/coding-assist`）。Windows は当面非提供。**GPU 搭載 Windows のみでの搭載を検討する** |
| 既定 ctx | **131072（128k）** |
| Agent ステップ上限 | **12** |
| 永続の最小 | 会話＋直近ワークスペース。索引キャッシュは任意／後続 |
| エディタ | **`re_editor` + `re_highlight`**（拡張子別ハイライト。§2.2）。Markdown／HTML 系は **ビュー切替**（§2.2.5）。**Dart 入力中補完**（§2.2.7）。**Swift 入力中補完・定義**（§2.2.8） |
| ワークスペース種別 | 走査時に `CodingWorkspaceKind` を判定し Agent system を切替（§0.3） |

### 0.6 製品方針（コーディング方向の継続拡張）

LMCode は **コーディングアシストが本流**。次を方針とする。

| 項目 | 方針 |
|------|------|
| 位置づけ | S16（および S11／IF）を本アプリの主機能として **継続拡張**する |
| 拡張の例 | 入力中補完（言語解析）、エディタ体験、Agent／差分、ワークスペース連携、ターミナル周辺など。**個別機能は問い合わせと工数で段階導入** |
| 非目標 | VS Code／Cursor の完全互換や、全言語の IDE 機能一括搭載は目指さない |
| 優先の型 | 要望が強く工数が抑えられるものから（補完は **Dart 実装済**。Swift は §2.2.8 で設計確定） |
| 設計の置き場 | 画面仕様は本ドキュメント（S16）。IF・データが必要になったら詳細設計の該当章を追加 |

## 2. 構成要素

| 要素 | 挙動 |
|------|------|
| 戻る | 本アプリでは起動画面のため原則なし（設定から戻るときは S16 へ pop）。**開いているタブに未保存があるとき、または表示中バッファがタブ内容と違うときは確認**（破棄して戻る／キャンセル）。未保存が無ければそのまま戻る |
| ワークスペース | 「フォルダを開く」（ダイアログ名は **プロジェクトフォルダを選択**）で選んだディレクトリが Agent／索引／ツールのルート（ツールバーに絶対パス表示）。走査で `CodingWorkspaceKind` を判定（§0.3）。直近は `coding_assist/` に記憶 |
| ブランチ | git リポジトリのときタイトル部に現在ブランチ名を表示（`CodingGit.currentBranch`）。非 git は非表示 |
| モデル | ツールバーで **コーディング用**のみ変更可（変更時サーバー再起動）。同じモデルの再選択は無視する。切替中は送信不可。完了または失敗で送信可否を戻す |
| **設定（歯車）** | モデルの右、RAM の左。タップで設定リスト（§2.5）。外観・フォント・インデント・思考・自動実行・スリープ・ハーネス定数。スリープ予定中は歯車を点灯 |
| **RAM 使用率** | 思考チップの右隣。**％のみ**表示（**5 秒**更新）。クリックで上位 **10** アプリの使用量リスト（**2 秒**更新）。リスト外クリックで閉じる。過大モデル選択の目安。実装: `CodingRamUsageIndicator`／`CodingSystemMemory`（macOS: `vm_stat`＋`ps`／Windows: PowerShell。**両 OS 必須**） |
| 外部非送信バナー | Agent ステータスに常時（§2.4） |
| 左メニュー | §2.1（折りたたみ: フォルダ／文言検索／Git commit） |
| コードエディタ | §2.2 |

| Agent／エラー解析 | §2.3 |

### 2.1 左メニュー（折りたたみ）

左ペイン全体を折りたたみ可（細いストリップ。**⌘B / Ctrl+B** またはヘッダの折りたたみ）。展開時は幅おおよそ 280。  
内部は **3 セクションを折りたたみ式**（既定: フォルダ操作のみ展開）。「メニューで表示」時は自動展開。

#### 2.1.1 フォルダ操作（階層ツリー）

VS Code のように **フォルダを展開／折りたたみ**して辿る。フラットな相対パス一覧ではない。

| 項目 | 方針 |
|------|------|
| データ | 相対ファイル＋相対ディレクトリからツリー構築（`CodingFileTreeNode`）。空フォルダも表示 |
| 並び | フォルダ優先・名前順（大文字小文字無視） |
| 操作 | フォルダ行: 展開／折りたたみ＋選択。ファイル行: タップでタブを開く |
| 行UI | 同階層のファイルとフォルダは**左インデントを同じ**にする。フォルダ行の先頭にフォルダアイコン（14px）。展開印は右端（16px）。行高はメニューフォント＋4（下限 18・上限 28）。ディレクトリとファイルを同じ高さにして階層を詰めて見せる |
| 移動 | **ドラッグ＆ドロップ**でフォルダ／ルートへ階層変更（同名衝突は拒否） |
| ヘッダ操作 | ルート名横にアイコンのみ: **新規ファイル**／**新規フォルダ**／**更新** |
| 新規作成先 | 入力がファイル名だけなら、選択ファイルと **同階層**（選択がフォルダなら **その中**。未選択はトップレベル）。入力に `/` を含むワークスペース相対パスなら **そのパスに作成**（メニュー選択位置は使わない）。**⌘N** もこの作成先で、名前は聞かず拡張子なしの `Untitled-1` から連番 |
| 更新 | 外部 IDE 等での増減を再走査。未保存タブは保持、保存済みはディスク再読込 |
| 初期展開 | 初回は `lib`／`test`／`ios`／`android` を開く。一度開いたワークスペースは、見えていたフォルダの展開／折りたたみを記憶し、次回そのワークスペースを開いたとき同じ状態にする。まだ表示していないフォルダは既定のまま（`index.json` の `folderTreeExpanded`） |
| 除外 | §4.2。除外パスはツリーに出さない |
| 未選択時 | 「フォルダを開く」＋最近使ったワークスペース一覧 |

#### 2.1.1a ツリー右クリック

| 対象 | メニュー |
|------|----------|
| ファイル | **RENAME**／**DELETE**。git があるとき **Git Add（ファイル）**。**名前のコピー**／**パスをコピー** |
| フォルダ | **RENAME**／**DELETE**。git があるとき **Git Add（フォルダ）**。**名前のコピー**／**パスをコピー**。**フォルダ構造をAgent貼り付け**（入力欄には書かず、送信前の付与項目）。**フォルダが持っているファイルを全てAgentに追加**（配下のテキストファイル本文を、開いているファイルと同じ送信前の取り込みにする。パス一覧ではない） |
| DELETE | 確認ダイアログ後に削除（フォルダは再帰）。開いているタブも閉じる |
| RENAME | 同階層での名前変更。タブパスも追随 |
| Git Add | `git add -- <相対パス>`（`CodingGit.add`） |
| 名前のコピー | 表示名（basename）をクリップボードへ。SnackBar で完了通知 |
| パスをコピー | ワークスペース相対パス（ファイル名含む。例: `lib/main.dart`）をクリップボードへ |
| フォルダ構造 | `CodingFileTreeNode.toAgentStructureBlock` を入力欄へは書かず、選択範囲と同じ送信前の付与項目にする。同じ相対パスは置き換え、別フォルダは並べる。送信時にユーザー文へ結合し、送信後は消す。入力が空でもこの付与だけで送信可。× で外せる |

#### 2.3.0 プロンプト補助メニュー（＋）

入力欄下の補助アクションが増えたため、**低い角丸ボタンの横並びはやめ**、**＋ 1 個**から PopupMenu で選ぶ。頻用アクションは **お気に入り最大2**を ＋ 隣の短縮ボタンで切り替える（ボタン行は **1行のまま**）。選択範囲付与以外は押下で **適用**し、送信は送信ボタンだけ。複数を重ねられる。**エラー解析**は他の補助と同時に適用しない。**タスク分解**と、**新規ソース提案を期待**・**修正ソース提案を期待**・**ドキュメント作成を期待**・**修正ドキュメント提案を期待**も同時に適用しない。後から押した方がもう一方を外す。

| 項目 | 方針 |
|------|------|
| 配置 | 入力 TextField（＋送信）の直下・左寄せ。`[＋][お気に入り…]` の1行。適用中があればその下に「適用」チップ |
| 見た目 | 低い角丸の **＋**（高さおおよそ 28）。Tooltip「プロンプト補助」。お気に入りは同じ高さの短いラベルボタン。適用中は色を変える |
| 押下 | メニュー一覧を表示。各項目に短い説明文（旧ボタンのホバーヒント相当）＋右端の ★。適用中はチェック |
| メニュー項目（順） | セレクト範囲情報をプロンプトに貼り付け／エラー解析／簡潔に表示／（区切り）／新規ソース提案を期待／修正ソース提案を期待／ドキュメント作成を期待／修正ドキュメント提案を期待／プログラム分析／タスク分解／タスク評価／テストを実行 |
| 適用 | 選択範囲付与以外は押下で適用／もう一度で解除。下書きは書き換えない。送信時に押した順で指示を重ねる（`codingAssistApplyPromptActions`）。セッションのみ（永続しない）。送信開始・新規会話・履歴を開く・WS を開くで解除。エラー解析は他の補助と同時に残さない。タスク分解とソース／文書の出力期待も同時に残さない（`CodingPromptAction.toggleApplied`）。送信した＋の ID と入力欄の依頼文は、その user メッセージの固定プロンプトとして残す |

#### 2.3.3 新規ソース提案を期待（暫定 UI）

ローカル LLM 向けに、Begin/End Patch 形式を依頼文へ明示付与するショートカット。見た目の整理は後続。

| 項目 | 方針 |
|------|------|
| 前提 | 送信時に入力欄へ依頼文がある、**または**取り込み／選択範囲があること |

| 送信時 | 適用中なら `codingAssistExpectFileOutputPrompt` で形式ルールを付与して送信 |

#### 2.3.4 修正ソース提案を期待（暫定 UI）

既存修正をローカル LLM に出させ、人がエディタで **関数全体を選択**→カードの **選択範囲を置換** で機械置換する前提のショートカット。行単位の断片だと置換ミスが起きやすいため、**関数（メソッド）単位**で出す。

| 項目 | 方針 |
|------|------|
| 前提 | 送信時に入力欄へ依頼文がある、**または**取り込み／選択範囲があること |

| 送信時 | 適用中なら `codingAssistExpectFixProposalPrompt` で Update 形式ルールを付与して送信 |
| 付与内容 | **関数単位**。既存修正は `-`/`+` と Patch 直前の **`置換範囲: 開始-終了`**（read_file の行番号。自動実行はこの範囲を + 側で置換）。**新規関数は + のみ**＋Patch 直前に **`挿入行: N`（1-based）必須**。文脈行不要・**1 Patch = 関数1つ**（@@ 1回）・複数は Patch 分割・クラス／ファイル全体の再掲禁止・変更行だけの断片禁止 |
| 配置 | ＋メニュー内 |

#### 2.3.5 選択範囲を置換／カーソル位置に挿入（修正ソース案カード）

| 項目 | 方針 |
|------|------|
| 対象 | pending の **Update**（`isAddFile=false`）。操作先は **いま開いているエディタ**（提案 path 一致は不要） |
| 既存修正 | `-` と `+` がある → タイトル「修正ソース案（関数単位）」。**対象関数全体を選択** → **選択範囲を置換** |
| 新規関数 | `+` のみ（`isInsertOnlyPatch`）→ タイトル「新規関数案（挿入）」。Patch 直前の **`挿入行: N`** をパースしてカード表示。**提案行があればその行の先頭へ挿入**（無ければカーソル位置。選択不要） |
| 表示 | **差分プレビュー（Phase 1）**: `-` 行＝薄赤、`+` 行＝薄緑（monospace・スクロール）。新規／Add は追加プレビューのみ |
| 複数 | 関数ごとに Patch＝カードが並ぶ（同じファイルでも関数が違えば別カード） |
| 処理 | 提案の新側（`codingAssistPatchReplacementBody`）で `replaceSelection`。タブ内容を Bloc に同期したあと **そのタブをディスク保存**。カードは **消さず `applied` 表示**（「閉じる」で除去可） |
| 失敗 | タブ未開封／（置換時）選択なし／新ソースなし → モーダル案内。ディスクは触らない |
| 自動実行 | Agent自動実行 ON のとき、hunk の一致に失敗した既存修正は **`置換範囲: 開始-終了`** の行を + 側で置き換える（人手の選択範囲置換と同じ差し替え。選択は不要）。範囲が無い、またはファイルの行数の外なら再提案。**新規関数（`+` のみ）で `挿入行: N` があるときは、その行の先頭へ挿入する**（行がファイルより先なら末尾）。中身があるファイルへの Add File は挿入せず、従来どおり再提案 |
| ソースをコピー | 作成・修正・挿入・適用済みの各カード。適用に使う新側（`codingAssistPatchReplacementBody`。`+`／`-` なし）をクリップボードへ。差分の `-`／`+` は表示専用で、範囲選択には含めない |
| その他 | 既存修正のみ **自動適用** 残置。新規挿入カードは自動適用を出さない。未適用は **却下**／**現状で再提案** |

#### 2.3.7 タスク分解（暫定 UI）

ローカル LLM にまとめて複数作業を頼むと精度が落ちるため、**依頼を細かいタスクに分解して提示するだけ**のショートカット。ソースやパッチは出させない。ユーザーは分解結果を見て、一つずつ別送信で実行する。

| 項目 | 方針 |
|------|------|
| 前提 | 送信時に入力欄へ依頼文がある、**または**取り込み／選択範囲があること |
| 押下 | **適用**（もう一度で解除）。送信しない |
| 送信時 | 適用中なら `codingAssistTaskDecomposePrompt` で分解指示を付与して送信（入力空＋添付のみも可） |
| 付与内容 | 最初に **目的:**（何を達成するタスクか。1〜2文）。続けて実行タスク。**クラウドより細かく詳細に**分解。各タスクに **（新規\|既存）相対パス — 何をするか** を必須。1タスク＝ファイル1つへの1作業。ソース／パッチ禁止 |
| 配置 | ＋メニュー内 |
| 実装メモ | `codingAssistTaskDecomposePrompt` |

プロンプト骨格（実装正）:

```text
【タスク分解の指示・最優先で厳守】
最初に「目的:」で、この依頼が何を達成するタスクかを書く。
続けて実行タスクを番号付きリストにする。
各タスクは「（新規|既存）相対パス — 何をするか」形式必須。
粗い大項目・パス無しは禁止。ソース・パッチ禁止。
```

#### 2.3.11 タスク評価

小さいローカルモデルは、タスク分解の同じ会話の続きだと「問題ない」とまとめ、検討が浅く終わる。**分解結果をコピーして新しい会話へ移し**、そこで評価させる。元の依頼文は渡さない。目的は分解結果の先頭に書いてある。

| 項目 | 方針 |
|------|------|
| 前提 | いまの会話に、タスク分解の応答があること。無いときはメニューを無効 |
| 押下 | **すぐに実行**。適用の切替ではない。下書きは送らない |
| 移行 | 新しい会話を作り、そこへ切り替える。元の会話は履歴に残す |
| 渡すもの | Agent が出したタスク分解（目的と実行タスク）。その分解の送信に付いていた取り込みファイル。ファイル本文は吹き出しに出さず、パスだけ残す |
| 渡さないもの | 元の依頼文。選択範囲とフォルダ構造。タスク分解の指示本文 |
| 出力 | `判定: 要修正` または `判定: このまま`。指摘を1行以上。要修正のときは直し後のタスク（目的と番号リスト）。ソース／パッチ禁止 |
| 配置 | ＋メニュー内、タスク分解の次。お気に入り短縮名は **評価** |
| 実装メモ | `codingTaskEvaluationSource`／`codingAssistTaskEvaluatePrompt` |

#### 2.3.8 テストを実行

「テストして」と毎回書かずに、今の実装を `flutter analyze` と `flutter test` に回す。他の＋項目と重ねられる（例: **新規ソース提案を期待** ＋ **テストを実行**）。文書だけの＋と重ねたときも、この項目が付いていれば検証する。

| 項目 | 方針 |
|------|------|
| 押下 | **適用**（もう一度で解除）。送信しない |
| 送信 | 適用中なら `codingAssistRunFlutterVerifyPrompt` を重ねる。入力が空でも送信可。印は `【テスト実行】`。この時点の返答では合否を書かない |
| 実行 | Flutter WS なら送信・自動書き込み（ON のとき）・再提案のあと §5.4.1。書き込みが無くてもこの送信では検証する |
| 報告 | 検証が終わったら `codingAssistFlutterVerifyReportPrompt` で Agent に書かせる。回答の最後は検証レポート（何をテストしたか、終了コードとログのどの行で合格か不合格か）。判定はコマンド結果に合わせ、パッチは出さない。印 `【テスト実行】` は付けない。人が停止したとき、コマンドを回していないとき（非 Flutter、起動失敗、パッケージ追加、作成待ち）は短い通知のまま |
| 自動実行 ON | 失敗したら既存のエラー解析で最大3セット。Add も自動作成されるので、新規ソース提案を期待と組むと作成→検証→修正の循環になる。3セット後も失敗なら、そこでレポートする |
| 自動実行 OFF | コマンドは回す。失敗しても自動修正はしない（ログをチャットに残す） |
| 非 Flutter | コマンドは実行しない。チャットにその旨を残す |
| 配置 | ＋メニュー末尾。お気に入り短縮名は **テスト** |

#### 2.3.9 ドキュメント作成を期待

文書の新規ファイルだけを出させるショートカット。ソース提案と同じ Add File 形式だが、**回帰テスト指示は付けない**。書き込み後の `flutter analyze`／`flutter test` も走らない。

| 項目 | 方針 |
|------|------|
| 前提 | 送信時に入力欄へ依頼文がある、**または**取り込み／選択範囲があること |
| 押下 | **適用**（もう一度で解除）。送信しない |
| 送信時 | 適用中なら `codingAssistExpectDocumentCreatePrompt` で形式ルールを付与して送信 |
| 付与内容 | 文書の Add File。**ディレクトリ付き**相対パス、`配置先:` 明示、`+` 行のみ、フェンス禁止。配置は既存の文書構成（例: `document/`）を確認してから決める。ソース・テスト・`pubspec.yaml` は禁止。既存文書の修正は「修正ドキュメント提案を期待」へ誘導 |
| 検証 | この＋だけ（簡潔など検証しない項目との併用を含む）なら §5.4.1 に入らない。**新規ソース提案を期待**・**修正ソース提案を期待**・**エラー解析**・**テストを実行**が同時なら、そちらの検証は残す |
| 配置 | ＋メニュー内。お気に入り短縮名は **作成** |

#### 2.3.10 修正ドキュメント提案を期待

既存文書を節または連続する範囲で直させるショートカット。関数単位ではない。回帰テスト指示は付けず、書き込み後の検証も走らない。

| 項目 | 方針 |
|------|------|
| 前提 | 送信時に入力欄へ依頼文がある、**または**取り込み／選択範囲があること |
| 押下 | **適用**（もう一度で解除）。送信しない |
| 送信時 | 適用中なら `codingAssistExpectDocumentEditPrompt` で Update 形式ルールを付与して送信 |
| 付与内容 | 既存範囲は `-`/`+` と Patch 直前の **`置換範囲: 開始-終了`**。新しい節は `+` のみと **`挿入行: N`**。1 Patch = 範囲1つ。Add File・ソース・テストは禁止。新規文書は「ドキュメント作成を期待」へ誘導 |
| 検証 | §2.3.9 と同じ。文書だけなら `flutter analyze`／`flutter test` は走らない |
| 配置 | ＋メニュー内。お気に入り短縮名は **文書** |

### 2.4 フッター（ステータス）

|------|------|
| Agent | 常時「Agentはオフライン動作（ネットワーク接続なし）」。続けて `model:` と `ctx:`。進行は起動、生成、ツール、圧縮、検証、パッチの適用・作成、会話、プロンプト補助。文言が無い起動中／生成中は「起動中」「生成中」 |

### 2.5 設定（歯車）

ツールバーの歯車でモーダルのリストを開く。表示・Agent・ハーネスは同じ一覧。値は端末に保存し、ハーネスは次の送信から使う（索引の件数は次の走査から）。

| 区分 | 内容 |
|------|------|
| 表示 | **外観**（システム／ライト／ダーク。`app_theme_mode`）。**個別色**（ライト／ダーク配色をピッカーで上書き。`app_color_overrides_*`）。メニュー／エディタ／Agent のフォント。インデント 2／4 |
| Agent | 思考、自動実行、自動実行後のスリープ |
| ハーネス | 生成、ループ、ツール、コンテキスト、検証。各行の下に範囲と、値を変えたときの効果をヒントとして出す。本文は §2.5.1 |

保存キーは `coding_ui_harness`（JSON）。モデルと ctx は S11 のまま。実装: `CodingHarnessSettings`。

#### 2.5.1 ハーネス項目と効果

歯車の「ハーネス」に並ぶ数値。各行はラベルと入力欄。その下に範囲と、表の「変えたときの効果」をヒントとして出す。既定は、設定画面を出す前までコードに固定していた値。範囲外は近い端へ寄せる。warn ＜ 自動圧縮 ＜ block を崩す入力は、保存時に 0.01 ずつ離して並べ直す。

効き始めは次の送信。**索引ファイル数**と**索引ツリー行**だけは、次にフォルダを走査したときから。チャットの吹き出し全文は、ここで短くしても消えない（短くなるのはツール結果の保存、API へ渡すビュー、検証ログ）。

本文の「12」「3回」「70%」「85%」「90%」などは、この既定を指す。歯車で変えた値がその回の動作になる。`read_file` を1応答で新たに開く件数（5）はハーネスに無く、固定。

##### 生成

送信ごとのサンプリング、待ち、トークン見積。見積はヘッダの `使用見込み / C` と、warn／圧縮／block の判定に使う（§4.5／§5.7）。

| 項目 | 既定 | 範囲 | 変えたときの効果 |
|------|------|------|------------------|
| temperature | 0.2 | 0〜2 | モデルの揺れ。上げると言い回しとパッチが変わりやすく、`-` 行が現状とずれる。下げると同じ依頼への返答が安定する |
| max_tokens | 0 | 0〜65536 | 1回の返答の上限。0 はサーバ既定（リクエストに載せない）。正の値にすると、そこで生成が止まる。小さいと Patch や tool の途中で切れる。大きいと1返答が長くなり、次ターンの見積を押し上げる |
| 接続待ち（分） | 5 | 1〜30 | `llama-server` の応答を待つ時間。上げると遅いモデルや長い思考を待ち続ける。下げると、その分数で生成を打ち切る |
| 見積（文字／トークン） | 2 | 0.5〜8 | 文字数をトークンに換える係数（文字数÷この値）。上げると使用見込みが小さく見え、warn・自動圧縮・block が遅れる（実トークンは ctx を超えうる）。下げると見積が大きくなり、まだ余裕があるうちに圧縮や block が始まる |
| 返答余白（ctx 比） | 0.12 | 0〜0.5 | コーディング用 ctx のこの割合を返答枠として使用見込みに足す。上げると履歴に使える枠が減り、圧縮と block が早くなる一方、返答が ctx 末尾で切れにくい。下げると履歴を多く載せ、返答の残り枠が減る |
| 思考の目安（字） | 400 | 50〜4000 | 思考 ON のときだけ system に「目安この字数」と書く。上げると長い思考を許す指示になる。下げると短く考える指示になる。ここで生成は止まらない。停止は次項 |
| 思考の打ち切り（字） | 8000 | 200〜100000 | 思考本文がこの字数を超え、まだ返答本文が無いときに生成を止める。上げると長考を許す（待ち時間とメモリが増える）。下げると空回りを早く切る（考えたあとに本文を出すモデルは、本文の前に止まる） |

##### ループ

1回の送信のなかで、ツールと再生成を何回続けるか。再提案と `read_file` の連続失敗もここ。

| 項目 | 既定 | 範囲 | 変えたときの効果 |
|------|------|------|------------------|
| ステップ上限（自動実行 OFF） | 12 | 1〜40 | 自動実行 OFF のとき、その送信でモデルを呼ぶ回数。上げるとツール往復が増え、パッチに届きやすい（時間と見積も増える）。下げると早く止まり、最後がツールのままだと「再生成に到達せず終了」になる |
| ステップ上限（自動実行 ON） | 12 | 1〜40 | 自動実行 ON の回数は、OFF の値とこの値の大きい方。この値を OFF より上げると、自動実行の往復がその数まで伸びる。OFF より下げても、ループは OFF の回数のまま。`read_file` の5件バッチとは別（§5.4） |
| 同一パスの自動再提案 | 1 | 0〜10 | 適用不一致や作成先の衝突で、同じ相対パスを自動でもう一度出させる回数。0 にすると自動では出さず、カードを人に残す。上げると、その回数まで現状を渡して出し直す。人手の「現状で再提案」はこの回数を外して実行できる（§5.6） |
| 同一パスの read 連続失敗 | 3 | 1〜20 | 同じ相対パスの `read_file` が本文なしで続いた回数。この回数に達すると、そのターンでは再試行せず、system の文言もこの回数になる。上げると誤パスを粘る。下げると早く人手取り込みに移る。一度成功すると回数は戻り、次の送信では数え直す（§5.2.2） |

##### コンテキスト

使用見込みがコーディング用 ctx の何割になったら警告・圧縮・送信停止するかと、圧縮後に何を残すか。自動実行 ON は自動圧縮の割合を待たず、毎回 §5.7.6 の作業記憶にする。warn と block はそのときも使う。

| 項目 | 既定 | 範囲 | 変えたときの効果 |
|------|------|------|------------------|
| warn（ctx 比） | 0.7 | 0.05〜0.95 | 使用見込みがこの割合以上でヘッダに注意を出す。送信は止めない。上げると注意が遅れる。下げると早い段階から注意が出る。自動圧縮以下に揃える |
| 自動圧縮（ctx 比） | 0.85 | 0.1〜0.98 | 自動実行 OFF で、次の API 送信前にこの割合へ達していたら §5.7.2 のテンプレ圧縮を行う。上げると全文に近い履歴を長く送る。下げると早い段階で古い tool がスタブになり、古い対話が要約になる。自動実行 ON ではこの割合は使わない |
| block（ctx 比） | 0.9 | 0.15〜0.99 | 圧縮したあともこの割合以上なら送信しない。上げると ctx ぎりぎりまで送る（サーバ側で溢れる余地が増える）。下げると早めに「新規会話」案内で止まる。自動圧縮より大きく揃える |
| 全文で残すターン | 3 | 0〜20 | 自動実行 OFF の API ビューで、直近いくつの user 以降の tool を全文のまま送るか。それより古い tool はスタブ（同一パスの `read_file` は、この窓の中でも最新1件だけ全文）。上げると最近の読取が残り、再読取が減る。下げるとスタブが増え、モデルが読み直す。0 だと tool はすべてスタブ |
| 圧縮時に残すターン | 1 | 0〜20 | テンプレ圧縮で、メッセージのまま残す直近 user の数。それより前は【これまでの要約】1本に畳む。上げると圧縮しても直近の往復が長く残る（減る量が小さい）。下げると多くの対話が要約だけになる。0 だと残すターンが無く、要約に寄せる |
| 自動実行で残す read | 2 | 0〜20 | 自動実行の作業記憶で、直前バッチ以外に全文で残す `read_file` の件数。優先は未適用パスと、最新エラーに出たパス。上げるとファイル本文が送信のたびに残り、見積が増える。下げるとパス一覧だけになり、モデルが同じファイルを読み直す。0 だと直前バッチ以外の本文は残さない（§5.7.6） |
| 要約に残す依頼 | 5 | 1〜30 | 要約と作業記憶の「これまでの依頼」に載せる user の件数。上げると古い目的が残る。下げると古い依頼が要約から落ち、モデルが初期の目的を忘れる |
| 要約1行（字） | 120 | 20〜1000 | 要約へ畳む user 1件の長さ。上げると依頼の文面が長く残る。下げると1行が短くなり、条件やパスが切れる |
| 要約に残すファイル | 20 | 1〜200 | テンプレ要約の「触ったファイル」に書くパス数。上げると多くのパスが要約に残る。下げると古いパスが要約から落ちる |
| 前回要約の再掲（字） | 240 | 40〜4000 | もう一度圧縮するとき、前回要約を1行にして残す長さ。上げると前の要約が次の要約に長く残る。下げると古い要約が早く短くなる |
| 検証ログの error 行 | 40 | 1〜400 | 自動実行の作業記憶で、最新の失敗ログから残す error／warning／FAILED／Expected の行数。上げると修正ターンが多くの診断を見る。下げると後ろの診断が作業記憶から落ちる |
| 検証ログの末尾行 | 15 | 1〜200 | 上の行が1行も無い失敗ログで、末尾から残す行数。上げると形式の違うログが長く残る。下げると末尾の数行だけになる |
| 直近応答を残す（字） | 4000 | 200〜50000 | 自動実行で、直前の assistant がこの字数を超えたら、tool フェンスと Patch の見出し行だけを残して短くする。上げると説明文も残りやすい。下げると説明が落ち、Patch 行だけが残りやすい |
| 直近応答の下限（字） | 800 | 50〜10000 | 直前応答に Patch 行も tool も無いとき、先頭から残す字数。上げると長い説明が作業記憶に残る。下げると説明だけの応答は短く切れる |
| 調査済みパス | 20 | 1〜200 | 作業記憶の「調査したパス」（全文を載せていない tool のパス）の件数。上げると調べた場所の一覧が長く残る。下げると古いパスが一覧から落ち、同じ探索を繰り返しやすい |

##### 検証

Flutter の analyze／test と、自動実行中に同じ回答・同じ失敗が続いたときの扱い（§5.4.1／§5.4.2）。自動実行 OFF では同一実行の検知は動かない。

| 項目 | 既定 | 範囲 | 変えたときの効果 |
|------|------|------|------------------|
| 修正セット | 3 | 1〜20 | 検証失敗のあと、エラー解析と自動書き込みを続ける回数。表示の `n/この数` もこれに合う。上げると失敗が続くあいだ自動修正が長くなる。下げると早く検証レポートに移り、その実行は止める（自動実行のスイッチは ON のまま） |
| flutter analyze（分） | 3 | 1〜60 | analyze を打ち切るまでの時間。上げると遅い解析を待てる。下げると時間切れになり、そのログで修正ループかレポートに進む |
| flutter test（分） | 10 | 1〜120 | test を打ち切るまでの時間。効果は analyze と同じで、対象がテスト全体 |
| 検証ログ（字） | 8000 | 500〜100000 | コマンド出力を残す文字数（末尾優先）。上げると失敗ログの前の方まで修正依頼とチャットに残る。下げると古い行が落ち、エラー抜粋の材料が末尾に寄る |
| 同一実行の会話移動 | 1 | 0〜10 | 同じ回答、または同じ失敗ログが続いたとき、新規会話へ移す回数。0 だと1回目から新規会話へ移さず、その実行だけ止める。1 だと1回移して続け、2回目で止める。上げると、同じ実行のたびに新しい会話で試す回数が増える。スイッチの自動実行は変えない |
| 同じ回答とみなす説明（字） | 80 | 0〜2000 | パッチが無い応答を「同じ回答」と比べるための説明の長さ。この字数未満の説明は検知しない（tool だけの応答も対象外）。上げると短い繰り返しはループにならない。下げると短い説明の繰り返しでも、新規会話への移動か停止が起きる。0 だと定型文以外の説明は長さに関係なく比べる |
| 同じ失敗ログとみなす長さ（字） | 40 | 0〜2000 | 失敗ログを同一実行と比べるための長さ（所要時間の差は無視）。上げると短い失敗はループにならない。下げると短い同一ログでも移動か停止が起きる |
| 新規会話へ載せる本文（字） | 4000 | 200〜50000 | 会話を移すとき、直前の実行と今回の実行として載せる本文（末尾を残して切る）。上げると新しい会話が直前の Patch やログを長く持つ。下げると新しい会話が見る材料が短くなる |

## 4. ワークスペースと多ファイル分析

### 4.1 原則

**全ファイルを毎回プロンプトに載せない。**  
長い ctx ＋ **索引／Agent の段階読取**。

**ワークスペースルート** = S16 でユーザーが開いたフォルダ（例: Flutter／Xcode／React／Android／Python プロジェクト直下）。  
相対パスはすべてこのルート基準（`README.md`・`lib/main.dart`・`src/App.tsx` 等）。アプリ本体のソースツリーではない。

```text
フォルダ選択 → 走査・除外・索引・プロファイル判定
  → ユーザー依頼（またはエラー解析）
  → Agent: list_dir / read_file / grep → Begin/End Patch
  → 差分カード → Apply / Reject / 現状で再提案 → ディスク書込
```

### 4.1a ワークスペースプロファイル判定

実装: `CodingWorkspaceKind`／`CodingWorkspaceKindDetect`（`coding_workspace_kind.dart`）。索引の相対パス一覧から判定し、`CodingWorkspaceIndex.kind` に保持。Agent system prompt にプロファイル名を付与。

| 優先 | kind | 判定ヒューリスティック（概略） |
|------|------|--------------------------------|
| 1 | `flutter` | ルートに `pubspec.yaml`（`ios/`／`android/` 同梱でも Flutter 優先） |
| 2 | `swiftXcode` | `Package.swift`、または `*.xcodeproj`／`*.xcworkspace`、または索引に `.swift` |
| 3 | `react` | `next.config.*`／`remix.config.*`、または `package.json`＋`.tsx`／`.jsx`（`fromRoot` 時は `package.json` 内の `react`／`react-dom`／`next` 依存も見る） |
| 4 | `android` | `AndroidManifest.xml`、またはルート `settings.gradle`／`settings.gradle.kts`、またはルート `build.gradle(.kts)`＋索引に `.kt`／`.java` |
| 5 | `python` | `pyproject.toml`／`requirements.txt`／`setup.py`／`Pipfile`、またはルート直下 `.py` |
| 6 | `generic` | 上記以外 |

`package.json` のみ（JSX/TSX なし・react 依存なし）は React にしない（Node 汎用と区別）。React Native（`package.json`＋JSX/TSX と `android/`）は React 優先。

### 4.4 索引

| 項目 | 方針 |
|------|------|

| ファイル数上限 | ソフト上限（実装: 5000）。超過時は省略注記 |
| キャッシュ永続 | 任意（後続）。都度走査でも可 |

### 4.5 コンテキスト予算

コーディング用 ctx を `C`（S11 選択肢に **131072＝128k**／**262144＝256k**。既定は 128k）。

| 項目 | 方針 |
|------|------|
| 内訳 | system＋ツリー要約＋**API 用履歴**＋返答余白（見積係数は S13 と同系統） |
| 2 層 | **UI／永続**は会話全文（tool は既存どおり截断可）。**API 送信**だけ圧縮ビューを組み立てる（§5.7） |
| しきい値 | `used / C` がおおよそ **70%** で warn、**85%** で自動圧縮を試行。圧縮後も足りなければ **block**（送信抑制＋案内）。**Agent自動実行 ON のときは 85% を待たず**、各 API 送信の直前に §5.7.6 |
| 超過時案内 | 第一候補は **「圧縮して続行」**（手動圧縮と同じ処理）。それでも不可なら新規会話を案内（S13 類似） |
| ヘッダ表示 | `使用見込み / C` は API ビュー基準。圧縮直後に再計算 |

詳細アルゴリズム・除外ルールは §5.7。

## 5. Agent プロトコル（アプリ主導）

### 5.1 原則

* ツール実行はアプリ。LLM に OS を直接触らせない  
* ディスク書き込みは **Update の適用**、**選択範囲を置換**、**提案行・カーソルへの挿入**、または **Add の作成** の成功時。Agent自動実行 ON では Update と Add の両方を自動で書く  
* 送信時は下書きに加え、**取り込み中ファイル**・**選択範囲**を合成してから Agent へ渡す（いずれも入力欄には書かない）  
* パース失敗時は再生成を促す  
* ファイルの有無は推測させない（無いと言う前に `list_dir`／`read_file`）  
* 同一パスの `read_file` が連続 3 回失敗したら中断し、読む予定のファイル一式の人手取り込みを頼む（§5.2.2）  
* ユーザーが取り込んだファイルは、そのターンでは再 `read_file` しない（§5.2.2）  
* LLM へ送る履歴は **必要最小**。古い tool 本文は再実行可能なので優先的に落とす（§5.7）  

### 5.2 ツール一覧（MVP）

| ツール | 内容 | 副作用 |
|--------|------|--------|
| `list_dir` | 相対パス一覧（除外適用）。パス救済あり（§5.2.1） | なし |
| `read_file` | テキスト読取（サイズ上限）。UI は折りたたみ。表示用に path を先頭付与可。パス救済あり。**同一ターンで成功したパスは再読取しない**（本文は返さず、既読である旨だけ返す。失敗は覚えず再試行可。次の送信・再提案・検証修正では再度読める）。**1応答あたり新たに開くのは5件**。超えた分は開かず、次の応答で読み直せる。バッチのあと既読一覧を返す。このバッチで開かなかったパスがあるときだけ、そのパスを `read_file` する。開き終えたあとは既読を `read_file` しない。まだ開いていない別のパスが必要なら、そのパスだけ `read_file` してよい。足りているなら完了の形に従う。**Agent自動実行 ON では実行しない**（§5.2.3） | なし |
| `grep` | テキスト検索（ヒット上限）。**既定はリテラル**部分一致。`regex:true` で正規表現。path がファイルならその1件のみ | なし |

パッチ提案は応答内の **Begin/End Patch**（ツール名 `propose_patch` を文中で案内してもよいが、適用キュー化はフェンス検出）。

#### 5.2.1 パス救済（実装済）

LLM のパス揺れをアプリ側で吸収する（`CodingPathResolver` / `CodingAgentTools`）。

| 項目 | 方針 |
|------|------|
| 正規化 | `` ` ``・引用符除去、`./` 除去、末尾 `/` 除去、WS 配下絶対パスの相対化。WS 名付き相対は、落とした残りが索引上のパスであるとき、または残りにもディレクトリが残るときだけ落とす。WS 名と同じ実ディレクトリ（例: `MyApp/ContentView.swift`）や、落とすとファイル名だけになる新規パスは残す |
| ソフト一致 | 大小無視の一意一致、**basename が一意**ならそのファイル／ディレクトリへ補正（補正時は結果先頭に注記） |
| 失敗時 | 「ありません」に加え索引からの **候補一覧**（最大おおよそ 8）。system で候補を使い直すよう指示 |
| 索引 | 走査済み `relativeFiles`／`relativeDirectories` をツールに渡す |

#### 5.2.2 read_file の連続失敗と人手取り込み

判定と依頼文は **system プロンプト**（`CodingWorkspaceKindDetect.systemPrompt`）。アプリは失敗回数を数えない。クリックで開く処理だけアプリ側。

| 項目 | 方針 |
|------|------|
| 対象 | `read_file`。本文が返らない結果（無い／読めない／path 空など）を失敗とする。截断つき本文は成功 |
| 回数 | **同一相対パスで連続 3 回**。依頼全体や `read_file` 全体の 3 回ではない。別パスの失敗は数えない。そのパスで一度成功したら回数は戻る |
| 中断 | 3 回目の失敗のあと、そのパスを再試行しない。追加の tool を出さず、そのターンを終える |
| 依頼範囲 | 初期調査などで、この依頼のために読むと分かっているファイルを**すべて**列挙する。失敗した 1 件だけにしない（A が 3 回失敗し、B と C も読む予定なら A・B・C） |
| 依頼文 | エディタで開き、タブ行の「取り込み」（今開いている／すべて）をするよう日本語で頼む |
| リンク | 各パスは `[相対パス](coding-file:相対パス)` のみ（コードフェンスで包まない）。クリックでその相対パスをエディタタブで開く（`CodingAssistOpenFileRequested`）。`..` や絶対パスは開かない。取り込み操作自体はユーザー |
| 次ターン | ユーザー発言に `【開いているファイル: path】` がある path は、その本文を正とし `read_file` しない。アプリはその path を開かず、「添付済み。このファイルは開いていません」を返す。載っていない path は Agent が `read_file` してよい |
| 実装 | プロンプト: `coding_workspace_kind.dart`。実行拒否: `CodingAgentTools.noteSuppliedPaths`（送信文の添付パス）。リンク: `coding_editor_file_link.dart`／Agent Markdown の `onTapLink` |

#### 5.2.3 自動実行 ON では read_file を実行しない

人が先にファイル本文を添付する。Agent は `read_file` で開かない。

| 項目 | 方針 |
|------|------|
| 対象 | Agent自動実行 ON のターンだけ。OFF は §5.2 のまま |
| 実行 | 応答の `read_file` は開かない。チャットには「このファイルは開いていません」だけを残す。本文は出さない |
| 変更案があるとき | 同じ応答に Patch があるなら、`read_file` は捨てて変更案を採用する |
| 不足パス | `read_file` の path、または本文の `不足:` の次行の相対パスを、アプリがこのターンで **1回だけ** 開く（最大5件。索引にあり、添付済みと既読は除く）。開けないパスは名前だけ残す。検証周期のあいだ、開いたパスと開けなかったパスは再要求しない |
| 検証の修正 | 失敗ログに出たパスを、未開封を優先して最大5件、最初の送信の API に載せる。チャットの吹き出しにはパス名だけ。本文があるときはエラー解析から `不足:` を外し、渡したファイルだけを直させる |
| 次の API | 添付の本文と、アプリが開いた本文を検査 API に載せる。チャットの吹き出しには本文を再掲しない。この API では `不足:`・`read_file`・`list_dir`・`grep` を書かせず、行番号は渡した本文の1行目から数える。開く前の system にある `不足:` の型は、この API の末尾で取り消す。その応答が再び `不足:` か `read_file` なら開かず、完了の形だけの再指示を1回出す。それでも成果物が無ければ止める |
| 行番号 | 置換範囲と挿入行は、渡された本文の1行目から数える。適用処理自体は `read_file` を呼ばない |
| 再提案 | 自動実行 ON の現状再提案は、渡した現状の行を使い `read_file` を出さない。OFF は従来どおり読んでもよい |
| 残るツール | `list_dir`・`grep`・シンボルツールは実行する。ファイル本文の代わりにはしない、と system に書く |

### 5.3 パッチ形式（MVP 固定）

```text
*** Begin Patch
*** Update File: lib/foo.dart
@@
 文脈行（先頭スペース）
-旧行
+新行
*** End Patch
```

| 項目 | 方針 |
|------|------|
| Update | **既存修正は `-` と `+` の両方必須**。人手置換前提では **関数単位**（関数全文の -/+）・文脈不要・**1 Patch = 関数1つ（@@ 1回）**（§2.3.4） |
| Add | 新規のみ `*** Add File:` ＋ `+` 行のみ可（コロン欠落もパース可）。**人の承認で機械作成**（§5.3.2）。パッチ Apply 経路には載せない |
| 適用アルゴリズム（Update・自動適用） | `rawDiff` を **hunk 単位**で適用。連続一致→行末空白差→差分行の個別置換→同一内容 hunk は no-op 成功。Agent自動実行で一致しない既存修正は、Patch 直前の **`置換範囲: 開始-終了`** を + 側で置換（§2.3.5） |
| 選択範囲置換（Update・主経路） | **いま開いているエディタ**の選択へ提案の新側を `replaceSelection`（提案 path 一致不要。§2.3.5） |
| ベース（自動適用） | 開いているタブ内容を優先。失敗時はディスク再読込して再試行 |
| 不一致（自動適用） | カード／SnackBar。続けて **現状ファイルを正とした再提案**（§5.6） |
| 単位 | Update: **選択範囲を置換**／却下／自動適用／現状で再提案。Add: **作成**／却下 |
| Equatable | pending の `errorMessage` 変化で UI が再描画されること（実装注意） |

### 5.3.1 system プロンプト上の編集規則（要約）

* ワークスペース相対パス。README／pubspec も対象  
* 既存修正は `-`/`+` ペア。削除のみなら `-` のみ可  
* `-` 行は `read_file` 結果と完全一致（省略・言い換え禁止）  
* **関数単位**で Patch に出す。既存修正は `-`/`+` と **`置換範囲: 開始-終了`**（自動実行はこの範囲を + 側で置換）、**新規関数は + のみ**（`挿入行: N` 必須・提案行へ挿入）。変更行だけの断片・クラス全体・ファイル全文の再掲は禁止。文脈行は不要  
* **1 Patch = 関数1つ**（`@@` は1回）。複数関数は Begin/End Patch を分ける（同ファイルでも可）。Markdown コードフェンスでパッチを包まない  
* 無関係なコメント追加や別関数の改変を1 Patch に混ぜない  
* **新規ファイル**は `*** Add File:`。アプリが作成する（Agent 自身はファイルを書かない）。自動実行 OFF では人の **作成**、ON では自動作成。既存ファイルの上書きはしない  
* 新規のパスは推測しない。list_dir／grep で既存構成・同種ファイルの置き場所を確認し、プロジェクト慣習に合わせる  
* Add File は **ディレクトリ付き**ワークスペース相対パス必須。Patch 直前に `配置先:` を書く。UI メニュー選択位置は作成先に使わない  
* 同一パスの `read_file` 連続 3 回失敗で中断し、読む予定ファイルを `coding-file:` リンクで人手取り込み依頼（§5.2.2）  
* `【開いているファイル: path】` がある path は再 `read_file` しない  

### 5.3.2 ファイル作成の承認（機械作成）

新規ファイルは **パッチ Apply（ベース照合）に載せない**。Agent自動実行 OFF では人がカードの **作成** で承認する。ON では応答完了後に同じ作成処理を自動で行う。

| 項目 | 方針 |
|------|------|
| 提案形式 | `配置先:` ＋ `*** Begin Patch` ＋ `*** Add File: ディレクトリ付き相対パス` ＋ `+` 行（§5.3） |
| 検出 | フェンスパースで `isAddFile=true` の pending（Update と同列の `pendingPatches`） |
| UI | **ファイル作成カード**（§6）。作成先パスを明示。**作成**／**却下**。作成先に中身があるときは **作成** の代わりに **既存を修正**／**別パスで作成**。作成後は適用済み表示＋**閉じる** |
| 作成処理 | `+` 行を連結した本文を **Add File 行のパスのみ**へ書き込み（左メニュー選択は参照しない）。親ディレクトリは再帰作成。パスは `CodingPathResolver` で正規化。ファイル名だけのパスは作成拒否。索引を再走査しタブを開く。カードは `applied` で残す |
| 照合 | ベースとの `-`/`+` 一致は行わない（文脈行があっても捨てて `+` のみ採用） |
| 既存衝突 | ディスクまたは開いているタブに **非空の内容**があるパスは作成しない（上書き禁止）。**Agent自動実行 OFF** ではカードに理由を出し、人が **既存を修正**（現状を正とした Update）か **別パスで作成**（別の Add File）を選ぶ。**ON** ではそこで止めず、対象のシンボルで一つの Patch に決めて出させる（同じ対象は Update、違う対象は対応する別パスの Add。そのパスが既にあればその Update。別パスを決められない、または開けないときは再提案しない）。同一パスの自動再提案は 1 回までで、2 回目はカードに残して人が選ぶ |
| 空パス | 未作成、または空ファイル／空タブなら本文で作成（空本文も可） |
| 自動適用 | Agent自動実行 **OFF** では人の **作成** クリック。**ON** では応答完了後に Update と続けて自動作成する。上書きはしない（§5.4） |
| 却下／閉じる | リストから除去（Update と同じ） |

#### 5.3.3 Flutter の回帰テスト

一部を直すと別の機能が壊れる、を `flutter test` で見つける。検証専用のテストをアプリが生成するのではなく、Agent が実装と同じ応答で `test/` の `*_test.dart` を出す。§5.4.1 の `flutter test`（引数なし）が、既存分と今回足した分をまとめて実行する。

| 項目 | 方針 |
|------|------|
| いつ | Flutter ワークスペースで、Dart の振る舞いを追加または修正するとき。平文送信は system。＋の新規ソース提案・修正ソース提案・エラー解析・テスト実行（実装を伴うとき）は user 側にも同じ文を載せる。**ドキュメント作成を期待** と **修正ドキュメント提案を期待** には載せない |
| 対象 | 今回変える振る舞いと、その変更で壊れうる隣接の振る舞い。実装の写経はしない |
| 配置 | 出す前に `list_dir`／`grep` で `test/` を見る。`lib/features/foo/bar.dart` なら `test/features/foo/bar_test.dart`。既存があれば Update、無ければ Add File。ファイル名だけは不可 |
| 依存 | `package:flutter_test` とテスト対象の import だけ。`pubspec.yaml` にパッケージ行を足さない |
| 出さない | コメント・文書・プロンプト文言だけ。テスト自身だけの修正。文法エラーだけで振る舞いが変わらないとき。Flutter 以外 |
| タスク分解 | パッチは出さない。対応する `test/` の `*_test.dart` を別タスクにする |
| 実装 | `CodingWorkspaceKindDetect.flutterRegressionTestRule`（Flutter の system と、上記＋メニューのプロンプト） |

### 5.4 ループ

1. ユーザー送信（通常／エラー解析／期待系ボタン／プログラム分析／タスク分解／現状で再提案）  
2. **送信前**に取り込みファイル・選択範囲を本文へ合成し、API 用履歴を組み立てる。自動実行 OFF はしきい値で圧縮（§5.7.2）。**ON は各 API 送信の直前に毎回** §5.7.6（検査と再指示は除く）  
3. 応答をフェンスパース（§5.5）  
4. ツール実行結果を **UI／永続 messages** に追加（自動実行 OFF は最大 **12** ステップ。ON は OFF の回数を下回らない。保存値が 5 でも 12 まで続く）。自動実行 OFF の `read_file` は1応答につき新たに **5** 件まで開き、既読の再指定は開かない。バッチのあと `【読み取りの報告】` で既読を返す。このバッチで開かなかったパスがあるときだけそのパスを読む。開き終えたあとは既読を読まず、まだ開いていない別のパスは `read_file` してよい。足りているなら完了の形に従う。既読だけの `read_file` が **2** 回続いたら、残りステップを使わず手順 7 の検査に入る。自動実行 ON の `read_file` は実行しない（§5.2.3）  
5. tool 追加後も見積を再評価し、必要なら次ステップの API ビューを再圧縮  
6. パッチは差分カード（Update）／ファイル作成カード（Add）へ（表示文から Patch／tool フェンス除去）。`*** Begin Patch` が `*** End Patch` より多い応答はカード 0 件。自動実行 ON で、タスク分解・プログラム分析以外なら、読み取りなしで書き直しを 1 回だけ出す。`不足:` があるときは開く方を優先する  
7. 上限／Stop／ツール無しで終了。上限はステップ回数（ON は OFF を下回らない）であり、read_file 5件ごとではない。自動実行 ON でその上限に達し、最後がツールのままなら、アプリが既読の `read_file` を検査する。検査は、その送信の固定プロンプトと入力欄の依頼文から完了の形を一つ書く。再指示は読み取りを許さない。検査と再指示の API は作業記憶を使わない。入力欄の依頼文と、人が添付した本文と、このターンでアプリが開いた本文と、その送信の指示だけを送る。＋の指示本文はチャットに出さず、検査と再指示の API では指示のあとに載せ、その末尾で `不足:`・`read_file`・`list_dir`・`grep` を禁止し、行番号は渡した本文の1行目から数える。開く前の `不足:` の型はここで取り消す。その応答が再び `不足:` か `read_file` なら開かず、完了の形だけの再指示を1回出す。それでも成果物が無ければ止める。それまでの ```tool 往復は載せない。検査のあと未読の `read_file` は開かない。完了の形がある応答の読み取りツールは実行しない。チャットの吹き出しは検査文と再指示文のままで、本文の再掲はしない  
8. S16 Agent自動実行 ON なら pending の **Update を順次 Apply** し、続けて **Add File を自動作成**する。作成先が既存の Add はカードで止めず §5.6 の再提案へ進む。それ以外で失敗した Add はカードに残す。**pubspec.yaml のパッケージ行は自動で書かない**  
9. Apply 不一致はキューし、ターン後に現状正で再提案ターン（§5.6）  
10. 再提案キューが空なら、Flutter かつ Agent自動実行 ON のとき §5.4.1。文書だけの＋（§2.3.9／§2.3.10）でソース系の＋が無いときは検証しない  
11. 応答または検証ログが直前と同じ実行なら、その時点で §5.4.2  

#### 5.4.1 Flutter 自動検証（analyze → test）

対象はワークスペース種別 `flutter` だけ。それ以外、またはこの周期で Update／Add を1件も自動で書けておらず、かつ＋の **テストを実行** も付いていないときは検証しない。**ドキュメント作成を期待** または **修正ドキュメント提案を期待** だけで、ソース系（新規ソース提案・修正ソース提案・エラー解析）も **テストを実行** も無い送信は、書き込みがあっても検証しない。`flutter build` と専用ビルド UI は持たない。設定キーは増やさない（既存の Agent自動実行を使う）。

| 項目 | 方針 |
|------|------|
| 開始 | 人の送信・プログラム分析・再実行でセット数を 0 に戻す。応答完了 → Update 自動適用と Add 自動作成 → 不一致の再提案が終わってから。＋の **テストを実行**（§2.3.8）が付いた送信は、書き込みが無くても検証する。自動実行 OFF でもコマンドは回し、失敗時の自動修正はしない |
| コマンド | ワークスペースルートで `flutter analyze --no-fatal-infos --no-fatal-warnings`。成功時のみ `flutter test --reporter compact`（テスト全体）。前段失敗時は後段を実行しない |
| flutter | S11 の Dart SDK から解決した `dart` の兄弟。無ければ PATH の `flutter` |
| 実行 | ヘッドレス（`Process.start`）。下部ターミナルには流さない。停止で子プロセスを終了する。analyze は 3 分、test は 10 分で打ち切り |
| ログ | 末尾優先で約 8000 文字。失敗時は既存のエラー解析プロンプトに載せ、user メッセージ先頭を `【自動検証 n/3】flutter analyze`（または `flutter test`）にする |
| 1セット | 失敗ログのエラー解析と、その修正の Update 自動適用／Add 自動作成。人の最初の依頼は数えない。最大 **3** セット。4回目の修正は始めない。この修正ターンの固定プロンプトは **エラー解析**（＋では他の補助と同時に押せない）。手順は `read_file` を書かせない。行番号は渡した本文の1行目。ログのパスは最大5件を先に渡し、そのときは `不足:` を書かせない。渡していないパスは書かせない。本文が無いときだけ `不足:` と相対パスだけ。完了の形は Begin/End Patch。`完了` だけ、または `*** End Patch` の無い Begin は未完了とし、読み取りなしの書き直しを1回出す |
| 書いたファイル | この周期で書いたパスは、次の自動実行で当初の添付本文を捨て、開いているタブかディスクの現状を読み直して渡す。書いていない添付はそのまま。チャットの吹き出しは当初の添付のまま |
| 成功 | チャットで Agent が検証レポートを書く（§2.3.8）。自動実行は ON のまま。セット数は戻す |
| 報告 | 成功、または失敗で自動修正を続けないとき（自動実行 OFF の失敗、3セット打ち切り、タイムアウト）。analyze と test のログを渡し、何をテストしどの結果で合格か不合格かを最後に書かせる。パッチは出さない。この報告から再検証は始めない。人が停止したときは報告しない |
| 作成待ち | 自動作成に失敗して Add が pending のまま残ったときだけループを止める。作成先が既存で §5.6 の再提案に進んだものは、ここでの停止にしない。それ以外はカードの理由を見て、必要なら **作成**。**自動実行は ON のまま** |
| パッケージ | `pubspec.yaml` にパッケージ行（`http:` など）がある提案は **自動で書かない**。カードに残し、この実行は止める。記述と `flutter pub get` は人。検証ログが未インストール（could not find package 等）のときも、修正ループに入らず同じ扱い。**自動実行は ON のまま** |
| 打ち切り | 3セット後も失敗、修正セットで Update も Add も1件も書けない（同じ段落を破棄して Patch が無いときを含む）、起動失敗、タイムアウト。この実行は止める。次の `flutter analyze` は始めない。**自動実行は ON のまま**（人が OFF にしたときだけ OFF）。コマンド結果があるときは検証レポート（§2.3.8）。起動失敗などは短い通知。人が停止したときは報告しない |
| 実装 | `CodingFlutterVerifyPolicy`／`CodingFlutterVerifyRunner`／`FlutterSdkResolver`。判定は Bloc に書かない |

#### 5.4.2 同一実行のループ検知

Agent自動実行 ON のあいだ、直前と同じ実行が続いたらループとみなす。自動実行 OFF では検知しない。人の送信・プログラム分析・再実行・手動の新規会話、および検証成功で回数は 0 に戻す。

| 対象 | 同じとみなす条件 |
|------|------------------|
| 回答 | パッチ本文、または 80 字以上の説明が、空白差を除いて直前の回答と同じ。ツールだけの応答は対象外 |
| コマンド結果 | 失敗した `flutter analyze`／`flutter test` のログが、所要時間を除いて直前の失敗と同じ |
| 生成中 | 1回の生成で、空白を畳んだ 40 字以上の段落、または「。」で区切った文が 3 回出る。その時点で生成を切る |

| 回数 | 動作 |
|------|------|
| 1回目 | 今の会話は履歴に残す。**最後に実行した内容**と**現在実行している内容**だけを載せた新規会話へ移し、自動実行は ON のまま続ける。同じ Patch・同じ修正は出さないよう指示する |
| 2回目 | 新規会話には移さない。この実行だけ止める。**自動実行は ON のまま** |
| 生成中 | その応答は破棄し、履歴には短い定型文だけを残す。Patch も `不足:` も無いものとして扱う。同じパスの自動再提案は、この応答からは始めない。自動実行は ON のまま |

実装: `CodingAutoLoop`（ターン間）。生成中は `codingGenerationRepeats`。判定は Bloc に書かない。

### 5.6 適用失敗時の再提案（現状を正）

| 項目 | 方針 |
|------|------|
| トリガ | Apply／自動適用でベース不一致。またはカードの **現状で再提案** |
| 入力 | 現状ファイル全文（上限あり）＋失敗した rawDiff＋状況別指示 |
| 指示分岐 | **未作成／空**（Update 適用失敗時）→ `*** Add File:` ＋ `+` のみ（以降は作成カード）。**通常 Update 失敗** → 現状一致の `-`/`+`。**作成先が既存の Add** は、自動実行 ON なら対象シンボルで一つの Patch に決める（§5.3.2）。二択は出させない。OFF、または同一パスの自動再提案が 1 回を超えたときは、人が **既存を修正** か **別パスで作成** を選んでから再提案（§5.3.2） |
| 旧パッチ | pending から除去し、新提案で置き換え |
| ループ防止 | 同一相対パスへの**自動**再提案は 1 回まで。手動「現状で再提案」はガード解除して再実行可 |
| 生成中の失敗 | キューし、生成完了後に再提案ターンを開始 |
| コンテキスト | 対象 path の現状全文が必須のため、**このターンは圧縮を弱める**（§5.7.4） |

### 5.7 コンテキスト圧縮（途中圧縮）

長会話・多 tool でも同一スレッドを継続するため、**API 送信ビューだけ**を途中圧縮する。UI 吹き出し・永続 `messages` の全文は消さない。

#### 5.7.1 原則

| 項目 | 方針 |
|------|------|
| 分離 | `messages`（UI／DISK）≠ `apiMessages`（LLM 送信） |
| 再読取 | 圧縮スタブと作業記憶は再読取を勧めない。同一ターンで成功済みの `read_file` は §5.2 のとおり再実行しない |
| パッチ | Begin/End Patch 全文を履歴に戻して肥大化させない（差分カードが正） |
| 見積 | ヘッダの `使用見込み` は `apiMessages`＋system＋下書き＋**取り込み中ファイル**＋選択範囲＋返答余白 |

#### 5.7.2 圧縮手順（優先順）

送信直前、および Agent ループ内の tool 追加後に評価する。

```text
estimate(apiMessages)
if used/C >= 0.85（または手動「圧縮」）:
  1. 古い tool 本文をスタブ化（直近おおよそ 2〜3 ユーザーターン分は全文維持）
  2. 同一相対 path の read_file は最新 1 件だけ全文、他は「既読」スタブ
  3. まだ超過なら、古い user／assistant を【これまでの要約】1 ブロックに畳む
  4. それでも不可 → block（送信抑制＋圧縮失敗／新規会話の案内）
if 0.70 <= used/C < 0.85:
  warn 表示のみ（自動圧縮はしない。手動圧縮は可）
```

**tool スタブ例:**

```text
[tool:read_file] lib/foo.dart
（圧縮済み・約 420 行。このパスは read_file しない）
```

**セッション要約スキーマ（固定。テンプレ優先、不足時のみ短い LLM 要約）:**

```text
【これまでの要約】
- 目的: …
- 触ったファイル: …
- 適用済み変更の要点: …
- 未解決: …
- 却下した案／やってはいけないこと: …
```

| 段階 | 実装方針 |
|------|----------|
| P0 | tool スタブ化＋同一 path 最新のみ（UI／保存不変）。**実装済**（`CodingApiContextBuilder`。送信時・見積とも API ビュー） |
| P1 | しきい値自動（85%）＋ヘッダ手動「圧縮」＋ warn／block。テンプレ要約で古い user／assistant を畳む。**実装済** |
| P2 | 不足時の短い LLM 要約強化。索引キャッシュ等（後続） |

#### 5.7.3 圧縮から除外（必ず残す）

1. 直近の user 依頼（編集中ならその文）  
2. 直近の assistant 応答と、その直後の tool 結果（パッチ整合のため）  
3. pending パッチの **path 一覧**（diff 全文は API に載せない。カード側が正）  
4. system の編集規則・ツール説明・ワークスペース／ツリー要約  

#### 5.7.4 例外: 現状で再提案ターン

§5.6 の再提案では対象ファイル全文が必須。

| 項目 | 方針 |
|------|------|
| 保護 | 対象 path の現状全文（再提案プロンプト内）と失敗 rawDiff 要約は圧縮しない |
| 弱め圧縮 | その他の古い tool は通常どおりスタブ化してよい |
| 衝突時 | 対象全文を載せると `C` に収まらない場合は block し、新規会話または対象ファイルだけの短い依頼を案内 |

#### 5.7.5 UI

| 要素 | 挙動 |
|------|------|
| 手動圧縮 | Agent ヘッダ「圧縮」。生成中は無効 |
| warn | 使用見込みが 70% 以上でヘッダ／Agent ステータスに注意表示 |
| 自動圧縮 | 自動実行 OFF では 85% 到達時、次の API 送信前に §5.7.2。ON では各 API 送信前に §5.7.6。ステータスに「コンテキストを圧縮して生成中…」等 |
| block | 圧縮後も余白不足なら送信不可＋「圧縮して続行」／新規の案内 |
| チャット表示 | 圧縮しても吹き出し内容は変更しない（API のみ） |

#### 5.7.6 自動実行中の毎回圧縮

Agent自動実行 ON のとき、85% を待たない。各 API 送信（tool のあと、検証の修正、検証レポートを含む）の直前に、UI／永続 `messages` は残したまま API ビューだけを作業記憶へ組み直す。見積も同じビュー。検査と再指示は作業記憶を使わず §5.4 の本文付き送信にする。自動実行 OFF は §5.7.2 のまま。要約生成に LLM は使わない。

先頭は `【自動実行の作業記憶】`。この周期の最初の送信で、畳む履歴がまだ無いときは依頼原文をそのまま送る。

| 項目 | API に残すもの |
|------|----------------|
| 依頼 | この周期のユーザー原文。続きの送信でも取り込みファイルの本文は残す。選択範囲の本文だけパスに落とす。この周期で書いたパスは、当初の添付を捨てて書いたあとの本文に置き換える（§5.4.1） |
| これまでの依頼 | それより前の user は1行に切る（最大5） |
| 実施済み | assistant の `*** Update/Add File` のパスと種別。未適用にあるパスは除く |
| 検証 | 過去の `【自動検証 n/m】` は1行。最新の失敗は `error`／`warning`／`FAILED`／`Expected` 等の行（最大40）。成功ログは「成功」 |
| 未適用 | pending パッチの path |
| 直前の tool | 直前の assistant 以降の tool 結果は全文 |
| `read_file` | 直前バッチ以外は最大2件。優先は未適用 path と、最新エラーに出た path。同じ path の古い本文は落とす。検査と再指示は作業記憶へ戻さず、§5.4 の本文付き送信に載せる |
| 調査したパス | 全文を載せていない tool の path（最大20） |
| 再提案 | いま返答する再提案だけ、現状全文と失敗 diff を残す。後続の検証送信ではパス1行 |

圧縮後も見積が block（90%）以上なら送信を止める。70% の warn は残す。

## 6. 差分・作成 UI

| 項目 | 方針 |
|------|------|
| Update 表示 | 修正: 「修正ソース案」＋**差分プレビュー**（赤-/緑+）。新規関数: 「新規関数案」＋**挿入行**＋**追加プレビュー**（緑+） |
| Update 操作 | 修正: **選択範囲を置換**。新規: **N 行目に挿入**（提案行あり）／**カーソル位置に挿入**（なし）（§2.3.5）。副: **却下**／（修正のみ）**自動適用**／**現状で再提案**／**ソースをコピー**（新側のみ。`+` なし）。適用後はカード残置（適用済み＋閉じる。ソースをコピーは残す） |
| Add 表示 | 「ファイル作成案」＋**追加プレビュー**（緑+。無ければ rawDiff） |
| Add 操作 | **作成**／**却下**（§5.3.2）。作成先に中身があるときは **既存を修正**／**別パスで作成**。**ソースをコピー**（`+` 行の本文のみ）。作成後もカード残置（適用済み＋閉じる。ソースをコピーは残す） |
| 複数 | キュー。**関数ごと**にカード。適用済みも残る。依存の自動解決なし。Add と Update が混在してよい |
| 自動適用 | S16 ツールバー `local_llm_coding_auto_apply_patches`（既定 false。表示「自動実行 ON／OFF」）。ON 時は応答完了後に **Update と Add File** を確認なしで書く。OFF の Add は人手の **作成**。Flutter は書き込み後に §5.4.1 |
