# S16 検討：ローカル LLM のシンボル探索

最終更新: 2026-10-16

**状態: 検討メモ（未採用）**。画面仕様の正本は [S16_コーディングアシスト.md](./S16_コーディングアシスト.md)。本ファイルは実装の指示ではない。

外部からの技術検討（「MCP を介した構造的ナレッジグラフ」）を、本アプリのコーディングアシスト（S16）に照らして整理した。提案者は本アプリの実装を前提にしていない。

---

## 1. 外部提案の要旨

ローカル LLM のコンテキスト窓を、ベクトル検索（RAG）で関連ファイルを丸ごと読む方式では埋めにくい、という問題設定。

| 比較（提案内） | 従来の RAG | 構造的ナレッジグラフ + MCP |
|------|------------|------------------------------|
| コードの捉え方 | テキストの塊 | AST の木 |
| 検索 | 意味が近い文を探す | 呼び出し元・定義などの依存を辿る |
| コンテキスト | 関連しそうなファイルを全文読む | 必要な関数・クラスの依存だけ取る |
| 得意 | 似た実装を探す | 変更の影響範囲を特定して直す |

提案された構成は「VSCode + Continue + Ollama」に、コード知識の MCP サーバを足すもの。実装手順は次の4段。

1. Tree-sitter で AST を取り、定義と参照を抽出する
2. NetworkX 等で「関数A → 関数B」のグラフをメモリか DB に持つ
3. MCP ツールとして `find_usages` / `get_dependencies` / `get_file_outline` を公開する
4. Tool Use 対応モデルに「修正前にグラフを調べよ」と指示する

代替案として、グラフを自前構築せず、LSP の「定義へ移動」「参照の検索」を MCP ツールにする、とある。

---

## 2. S16 に照らした結論

持ち込めるのは **探索の精度を上げる3点**。提案のシステム構成（VSCode / Continue / Ollama / 独立 MCP サーバ / Tree-sitter グラフ）はそのまま採用しない。

S16 はすでに、全ファイルを毎回プロンプトへ載せず、Agent が `list_dir` / `read_file` / `grep` で段階的に読む。コンテキストは既定 128k（最大 256k）で、古い tool 本文は圧縮する（正本 §4.5／§5.7）。エンジンは `llama-server`。ツール実行はアプリ側で、モデルは ```tool フェンスで依頼する。

不足は窓の長さより、**文字列の `grep` では定義と使用箇所を分けられない**こと。コメントや同名メソッドが混ざり、当たったあと `read_file`（最大 8 万文字）が履歴に積まれる。Agent のステップ上限は 12。

Dart Analysis Server と `sourcekit-lsp` は入力補完と定義吹き出しにだけ使っている（§2.2.7／§2.2.8）。Agent からは見えない。

## 3. メリット

| 項目 | 内容 |
|------|------|
| 影響範囲の特定 | `find_references` は同名の別シンボルやコメントを、名前の部分一致より切り分けやすい。リネームやシグネチャ変更の前調査に向く |
| 窓の節約 | ファイル骨格と参照一覧を「パス・行・前後数行」で返せば、探索のたびにファイル全文を積まなくてよい |
| 既存資産 | Dart と Swift の言語サーバは起動済み。定義取得の経路もある。新しい解析器を同梱しなくてよい |
| 編集規則との両立 | 変更する関数だけ従来の `read_file` を読めば、Patch の `-` 行を原文一致させる規則（§5.3）を維持できる |
| モデル非依存の地図 | 開いているファイル周辺のシグネチャを system の木要約の隣に載せると、ツール選択が弱いモデルでも「どこに何があるか」が届く |

提案の比較表のうち、「似た文章を探す」と「依存を辿る」の役割分担は妥当。S16 が欲しいのは後者に近い。

## 4. デメリット・合わない点

| 項目 | 内容 |
|------|------|
| 比較相手が RAG | S16 の現状はベクトル検索ではない。置き換え対象は `grep` と全文 `read_file` |
| Tree-sitter は意味解析ではない | 構文木から取れるのはファイル単体の見た目。import の別名、同名メソッド、extension、protocol、オーバーロードは解けない。Aider の repo map（tree-sitter + PageRank）も、大きいコードベースでは頻出メソッド名が上位を埋めることが知られている |
| グラフ結果だけでは編集できない | S16 の修正は原文の `-` 行が必須。影響一覧のあと、対象関数の本文は読む必要がある。窓の上限と圧縮（§5.7）は残る |
| MCP は運び方 | ツールの中身が同じなら、独立プロセスにしてもモデルが見る情報は変わらない。正本の原則は「ツール実行はアプリ。LLM に OS を直接触らせない」（§5.1） |
| 構成が別製品 | Ollama の Tool Calling 必須、という要件は `llama-server` にそのまま乗らない。ローカルの中規模モデルはツール選択が不安定で、フェンスのままツール種類を増やすと形式崩れが増える |
| 常駐グラフの同期 | 未保存タブを正にしている S16 では、ディスク上の静的グラフが古い参照を返す。言語サーバへ未保存バッファを渡す方が、補完側の同期と揃う |
| 言語カバレッジ | React / Python / Kotlin には言語サーバがまだない。同時に足すと、ユーザ端末の `tsc` や Pyright などの配布・検出が別作業になる |
| 配布方針 | Dart SDK も SourceKit も端末にあるものを使う。Python + NetworkX のサイドカー同梱とは合わない |

## 5. 効果がありそうなこと

優先度は上から。

1. **Dart の参照検索とファイル骨格を Agent ツールにする**  
   サーバが既にある。同名が多い Flutter の `lib/` で、`grep` の誤ヒットと全文読取が減る見込みが一番大きい。
2. **Swift でも同じ4ツールを、`sourcekit-lsp` が起動しているときだけ有効にする**  
   参照検索は索引が要る。補完が動いているプロジェクトに限る。
3. **ツール結果を短く切る**  
   参照は位置と前後1行、骨格はシグネチャと行番号。ヒット上限を設ける（現行 `grep` は 40 件）。本文が要るときだけ `read_file`。
4. **取り込み中ファイルとアクティブタブの定義一覧を、system のツリー要約（おおよそ 400 行）の隣に載せる**  
   ツールを呼ぶ前の地図。永続グラフは作らない。
5. **構造化 tool call**  
   正本 §5.5 の将来拡張。シンボルツールを増やしたあと、フェンスの形式崩れが目立つなら同じ段で見る。エンジンは `llama-server` のまま。

効果が見えにくいもの:

* 「修正前にグラフを調べよ」というプロンプトだけの追加。ツールが無いと `grep` に戻る。12 ステップも早く消費する。
* 独立 MCP サーバ、Tree-sitter からの常駐グラフ、SQLite / SCIP の全プログラム索引。言語サーバがライブで参照を返せるあいだは、同期コストの方が大きい。
* グラフによる Patch 精度の改善。原文一致と、適用失敗時の再提案（§5.6）は別問題のまま残る。

## 6. 今考えられる実装手順

仕様化は、効果を見てから正本（S16 §5.2）へ書く。手順は次のとおり。

### 6.1 Dart の Agent ツール（第一歩）

対象は Dart ワークスペースで Analysis Server が起動しているとき。失敗時は従来の `list_dir` / `read_file` / `grep` だけにする。

| ツール | LSP | 戻り |
|--------|-----|------|
| `file_outline` | `textDocument/documentSymbol` | 型・関数と行番号。本文は返さない |
| `workspace_symbol` | ワークスペースのシンボル検索 | 定義候補（パス・行・種別）。同名は候補一覧 |
| `go_to_definition` | 既存の definition | 定義のパスとシグネチャ付近 |
| `find_references` | `textDocument/references` | パス・行・前後1行。件数上限 |

実装の足場は `lib/features/coding_assist/data/dart_analysis_server_client.dart` と `CodingAgentTools`。未保存タブを正にする同期は補完側に合わせる。system プロンプト（`coding_workspace_kind.dart`）に、影響範囲は `find_references`、編集対象の原文は `read_file`、と書く。

確認すること:

* 同名メソッドで `grep` より参照件数が絞れるか
* 1 回のツール結果が窓見積をどれだけ増やすか
* フェンス JSON の失敗が増えないか

### 6.2 Swift

§6.1 と同じ4ツールを、`sourcekit-lsp` と BSP が起動しているプロジェクトだけ有効にする。未検出・スキーム不一致のときは Swift 側だけオフ（補完と同じ。Agent 自体は継続）。

### 6.3 プロンプト用のシンボル地図

開いているタブと取り込み中ファイルについて、`file_outline` と同系のシグネチャだけを system の木要約の隣へ載せる。トークン上限を決め、超えたら省略する。ツール呼び出しに依存しないので、§6.1 の成否と独立に試せる。

### 6.4 その後に見るもの

* フェンス崩れが増えたら、構造化 tool call（§5.5 経路 A）
* React / Python / Kotlin は、その言語のサーバを S16 に載せる判断が付いてから
* 常駐グラフや MCP 分離は、言語サーバの参照では足りない不足が具体化してから
