# ハーネス初期値の根拠 — 決定記録（Decision Records）

最終更新: 2026-11-20  
対象: [13_ハーネス数値棚卸し_パターン分け一覧.md](./13_ハーネス数値棚卸し_パターン分け一覧.md)（初期採用版）  
上位: [10_クライアント実運用と運用パターン_実装方針.md](./10_クライアント実運用と運用パターン_実装方針.md)

本ドキュメントは、**「なぜ初期はこの値・この区分で実装したのか」**を残す。  
後から値を変えたくなったときに、**当時の前提・検討した代替案・見直しのきっかけ・測る指標**を確認できることが目的である。

> **重要:** 13 の数値の多くは **実測前の推定（[推]）**または**現行値の維持（[現]）**である。  
> [現] は「変える理由が無かった」ことの根拠であり、「最適である」ことの根拠ではない（前提 P6）。

---

## 1. 使い方

| 場面 | 手順 |
|------|------|
| 値を変えたい | 13 の該当行の「根拠」列 → 本書の DR を読む → **見直しトリガー**に当てはまるか確認 → **指標**で実測 → §6 に記録 |
| 区分（A／D／S／F）を変えたい | DR-01／DR-02 の基準に照らす。固定→可変に昇格する手順は DR-12 |
| 新しいハーネス項目を足す | DR-02 の基準で A／D／S／F を決め、DR を追加 |
| 症状から原因を探す | §5 の早見表 |

## 2. 前提・仮定

初期値はこれらを前提にしている。**前提が崩れたら DR を見直す。**

| ID | 前提 | 出典・性質 |
|----|------|------------|
| P1 | 対象は **クライアント PC**（目安 RAM 16〜32GB）。サーバー級 GPU は想定しない | 00 §3 |
| P2 | モデルは **10B〜26B**。標準運用は 〜14B（第一候補は Gemma 4 系 〜12B） | 00／10 |
| P3 | `charsPerToken`：コード中心 **2**、日本語文章 **1.5**（いずれも概算） | 現行値＋推定。未実測 |
| P4 | ファイル 1 行は約 **40 字**（行数換算の目安） | 推定 |
| P5 | **[推] の値は未実測**。H9 で検証する | 12 H9 |
| P6 | **現行値の出自は経験的**で、設計上の根拠記録が無い。[現] は「維持」であって「最適」の保証ではない | 棚卸し時の確認 |
| P7 | ユーザー所感（2026-11-20）：**生成失敗・エラーがストレス**、**思考がループ要因**、**速度（現実的な体感）を重視**、**細かい設定はユーザーに任せられない** | 方針議論 |
| P8 | 検証レイヤ（analyze／test）は **Flutter 第一**。他言語 WS では未使用 | S16 |
| P9 | KV キャッシュと prefill 時間は **ctx にほぼ比例して増える**（一般的性質。具体値は未計測） | 一般知識。要実測 |
| P10 | `llama-server` は 1 構成のみロード。ctx 変更はサーバー再起動を伴う | S11 §4.2 |

## 4. 決定記録

<a id="dr-01"></a>
### DR-01 パターンで変える項目を約 10 に絞る

| 項目 | 内容 |
|------|------|
| **決定** | パターン（軽快／標準／深掘り）で変えるのは **コーディング・文章とも約 10 個**。残りは固定（F）・ctx 連動（D）・系統固定（S） |
| **経緯** | 当初案は **34 項目**を可変（13 初版）。レビューで「**検証しきれない**」と判断し絞った |
| **根拠** | ① 6 パターン × 34 項目は実測・回帰テストの組合せが現実的でない（前提 P5）。② ユーザーが体感する軸は「**待ち時間／失敗への粘り／根拠の厚さ**」の 3 つに集約でき、多くのつまみはこの軸に寄与しない。③ ハーネス細設定はユーザー負担が大きいという要件（P7） |
| **検討した代替** | **34 項目可変**：表現力は高いが実測不能・説明不能。却下。**2 択（速い／丁寧）のみ**：Web・RAG・検証の差を表せない。却下 |
| **見直しトリガー** | 実測で、固定にした項目が失敗率・速度に有意に効くと分かった（→ DR-12 の昇格手順） |
| **指標** | 項目別の感度分析（1 項目だけ変えたときの成功率・完了時間の変化） |
| **影響** | 13 §4 全体 |

<a id="dr-02"></a>
### DR-02 可変／固定の判断基準

| 項目 | 内容 |
|------|------|
| **決定** | 次の **4 条件のうち 3 つ以上**を満たす項目だけパターンで変える（A）。ctx から式で決まるものは D、系統で値が違うがパターンでは不変なものは S、それ以外は F |
| **基準** | ① ユーザーが**速さ・失敗しにくさ・根拠の厚さ**として体感できる　② 効果が **ctx の約 5% を超える**　③ 軽快と深掘りで**最適値が逆**になる　④ **実測で差を確認できる** |
| **根拠** | 実測可能な数に絞るための機械的な線引きが必要（DR-01）。「何となく変えたい」を排除する |
| **見直しトリガー** | 基準自体は、実測の結果「基準を満たさないが効く項目」が出たとき見直す |
| **影響** | 区分の全判断 |

<a id="dr-03"></a>
### DR-03 ctx を 32k／64k／128k の 3 段階、標準は 64k

| 項目 | 内容 |
|------|------|
| **決定** | ctx：軽快 **32768**、標準 **65536**、深掘り **131072**（文章・コーディング共通）。256k は推奨しない。現行既定 131072 は**深掘り相当**になる |
| **根拠** | ① プロダクト方針が**クライアント実運用・体感速度優先**（00／10）。現行 128k 既定は「14B 以上・32GB・長大 ctx」前提の旧方針由来。② KV キャッシュと prefill は ctx に比例（P9）。16〜32GB のクライアントで 10〜14B と併用すると 128k は余裕が小さい **[推]**。③ 日常のコーディング依頼は、system＋読取（1 ファイル ctx の 20%）＋履歴で足りるという仮説 **[推]** |
| **検討した代替** | **標準 128k（現行維持）**：方針と不整合、体感が遅くなる仮説。却下。**標準 32k**：検証ログ＋読取で block 到達が増える仮説。却下。**マシン診断で自動決定**：有望だが初期スコープ外（後続候補） |
| **前提** | P1, P2, P9 |
| **見直しトリガー** | 標準で **自動圧縮／block の到達率が高い**（案: 全ターンの 20% 超）→ 上げる。標準で **TTFT／完了時間が許容外**（案: 初回応答が体感で遅い）→ 下げる。モデルを 26B 級に変えて挙動が変わった |
| **指標** | ctx 別の TTFT、トークン／秒、メモリ使用量、自動圧縮・block 到達率、読取不足による再 read 回数 |
| **影響** | X01、D 区分（DR-08）、G05 |

<a id="dr-04"></a>
### DR-04 `maxTokens` を 0 から有限値へ

| 項目 | 内容 |
|------|------|
| **決定** | 0（サーバ既定＝実質無制限）をやめ、コーディング **4096／8192／12288**、文章 **4096／8192／16384** |
| **根拠** | ① 小〜中規模モデルは**暴走生成・繰り返し**で時間を失いやすく、ユーザーの最大のストレスである「生成失敗」の一因（P7）。② 返答余白（G05）を決めるには**返答の上限が必要**。③ 標準 8192 は、現行契約「1 Patch＝関数 1 つ」「複数は分割」（S16 §2.3）の返答が収まる量と推定 **[推]** |
| **検討した代替** | **0 を維持**：暴走を防げない。却下。**一律 4096**：深掘りや文章長文で切れやすい。却下 |
| **前提** | P7、S16 の Patch 契約 |
| **見直しトリガー** | `finish_reason=length`（上限切れ）で **Patch／ツール呼び出しが途中で切れる**率が高い（案: 5% 超）→ 上げる。空応答や繰り返しが多い → 下げる |
| **指標** | 上限切れ率、空応答率、1 返答あたり平均トークン、完了時間 |
| **影響** | G02、G05（返答余白） |

<a id="dr-05"></a>
### DR-05 ステップ上限の三段階と L02 の統合

| 項目 | 内容 |
|------|------|
| **決定** | コーディング **6／12／16**、文章 **4／8／12**。`maxAgentSteps` と `maxAgentStepsAuto` は**同値**とし、実装は 1 値へ統合（互換のため両フィールドは残してよい） |
| **根拠** | ① 標準 12 は**現行維持**［現］。② 軽快は半分：失敗時に長く待たせず人手へ戻す（待ち時間軸）。③ **深掘りでも 16 止まり**：ステップを増やすとループが悪化するというユーザー所感（P7）。深掘りの差は「参照・検証の厚さ」で出し、step の青天井にはしない。④ 文章は読取が少ないため低めでよい **[推]**。⑤ L02：自動実行 ON の回数は「OFF の上限とこの値の**大きい方**」（ソースの説明）。現行は同値 12 で**独立に持つ意味がない** |
| **検討した代替** | **深掘り 24〜40**：ループ・時間増大のリスク。却下。**軽快 8**：待ち時間短縮が弱い。保留（トリガー参照） |
| **見直しトリガー** | 軽快で「**ステップ不足で終了**（最後がツール呼び出しのまま）」が多い → 8 へ。深掘りで**後半ステップの成功率が低い**（増やしても伸びない）→ 下げる |
| **指標** | ステップ別の累積成功率、上限到達で終了した割合、ループ検知（V05）発動率 |
| **影響** | L01、L02 |

<a id="dr-06"></a>
### DR-06 検証セット数 2／3／4

| 項目 | 内容 |
|------|------|
| **決定** | `maxVerifySets`：軽快 **2**、標準 **3**（現行維持）、深掘り **4**。コーディングのみ（文章は検証を回さない） |
| **根拠** | ① 標準は**現行維持**［現］。② 軽快：1 セットは analyze（最大 3 分）＋test（最大 10 分）まで膨らみうるため、**失敗時の待ち時間を抑える**。③ 深掘り：失敗時の根拠取得（09 手法 B）を併用する前提で**再挑戦を 1 回増やす** **[推]**。④ 同種の失敗の繰り返しは回数を増やしても無駄なため、ループ検知（V05）と併用 |
| **注意** | 09 の手法 B（失敗駆動 Web 検索）は**未実装**。当面、深掘りの差は「再試行回数」のみ |
| **前提** | P8 |
| **見直しトリガー** | **n 回目で通る割合**を見て、3 回目以降の成功率が低ければ標準を 2 に。深掘りで 4 回目に通る割合が高ければ維持／強化 |
| **指標** | セット別の検証通過率、打ち切り率、検証に要した総時間 |
| **影響** | V01 |

<a id="dr-07"></a>
### DR-07 thinking：コーディング常時 OFF、文章は深掘りのみ ON

| 項目 | 内容 |
|------|------|
| **決定** | コーディングは**全パターン OFF**。文章は**深掘りのみ ON**。thinking 関連の値は系統固定（S）：コーディング `reasoningAbortChars` 4000（`thinkingGuideChars` は現行維持）、文章 `thinkingGuideChars` 800・`reasoningAbortChars` 12000 |
| **根拠** | ① ユーザー所感「思考がコーディングのループ要因になる」（P7）。② S11 の現行説明も「ON は遅延・空応答になりやすい」。③ **深掘り＝thinking ON ではない**（深掘りは参照・検証を厚くする。10 §3.2）。④ 文章は検証・パッチ契約が主でなく、推敲で効く余地があり、ループの害が相対的に小さい（ユーザー決定 2026-11-20）**[推]**。⑤ 文章の目安 800・打ち切り 12000：現行 8000 では長考後に本文が出る前に切れる恐れがあるため緩める **[推]**。⑥ コーディングの 4000：ユーザーが詳細設定で ON にしたときの**空回り保険** |
| **検討した代替** | **全パターン OFF 統一**：シンプルだが、文章の推敲品質の余地を捨てる。保留（トリガー参照）。**コーディング深掘りだけ ON**：ループ要因のため却下 |
| **見直しトリガー** | 文章深掘りで **ON と OFF を比較して品質差が無い** → OFF に統一。**空応答・打ち切り切断**が多い → 打ち切りを緩める／OFF。コーディングで**思考 ON が有意に有利**と分かった（モデルの世代交代など） |
| **指標** | 文章：ON/OFF の一貫性・用語統一の評価、空応答率、打ち切り切断率、完了時間 |
| **影響** | X02、G06、G07 |

<a id="dr-08"></a>
### DR-08 字数系を ctx 連動式（D）にする

| 項目 | 内容 |
|------|------|
| **決定** | `chars = ctx × charsPerToken × 比率`。比率：**読取・取り込み 20%**、**再提案 18.75%**、**ツール結果クリップ 9.2%**、**system 樹 4.6%（上限 8,000）**。`replyReserveRatio` は `maxTokens/ctx`＋余裕 |
| **根拠** | ① 現行は字数が**絶対値**で ctx と非連動（棚卸し所見 1）。ctx をパターンで変えると**整合が崩れる**。② 再提案・クリップ・樹の比率は、**標準（64k）で現行値に一致するよう逆算**し、標準の挙動を現行から動かさない。③ 読取のみ意図的に現行から引き下げ（DR-09） |

**算出結果（コーディング cpt=2）**

| 項目 | 比率 | 32k | 64k | 128k |
|------|------|-----|-----|------|
| 読取・取り込み | 20% | 13,000 | 26,000 | 52,000 |
| 再提案 | 18.75% | 12,000 | 24,000 | 48,000 |
| ツール結果クリップ | 9.2% | 6,000 | 12,000 | 24,000 |
| system 樹（上限 8,000） | 4.6% | 3,000 | 6,000 | 8,000（上限） |

文章（cpt=1.5）は同じ比率を適用（読取 9,800／19,600／39,000 など。13 §4.3）。

| 項目 | 内容 |
|------|------|
| **検討した代替** | **字数を固定のまま**：ctx 変更で枠超過か過小。却下。**トークン数で直接管理**：実装コスト大。後続候補 |
| **見直しトリガー** | 切り詰めによる**再 read 多発**・再提案不一致 → 比率を上げる。block 到達が多い → 比率を下げる。**実トークンと見積（cpt）の乖離**が大きい → DR-11 |
| **指標** | 再 read 回数、再提案不一致率、block／自動圧縮到達率、実トークン対見積比 |
| **影響** | T01, T02, T13, T14, T18, G05 |

<a id="dr-09"></a>
### DR-09 読取は ctx の 20%、バッチと合計予算で超過を抑える

| 項目 | 内容 |
|------|------|
| **決定** | `maxReadChars`／`openFileMaxChars` は **ctx の 20%**（標準 26,000 字）。`codingReadFilesPerBatch` は軽快 **3**／標準 **5**／深掘り **5**。**1 ターンの読取合計予算**（ctx の 50%）を新設（実装時） |
| **根拠** | ① 現行 80,000 字は cpt=2 で約 40k トークン。**64k ctx の 61%、32k では 122%** で、1 回で枠を超える（P3, P9）。② 当初案の 37.5% でも、**1 応答で 5 ファイル読む（現行バッチ 5）と 5×37.5% で超過**しうる。③ 20% なら標準で 26,000 字≒約 650 行（P4）を 1 回で読め、通常のソースには十分と推定 **[推]**。④ バッチ 5 件分の合計は新設の**合計予算**で守る。軽快（32k）はバッチも 3 に減らす **[推]** |
| **現行からの逸脱** | **これが現行値からの唯一の意図的な引き下げ**（DR-08 の他の比率は現行一致）。深掘り（128k）でも 52,000 字で、現行 80,000 字より小さい |
| **検討した代替** | **37.5%**（当初案）：バッチと合わせて超過。却下。**現行維持 80,000**：ctx を下げる方針と矛盾。却下。**20% だが合計予算なし**：理論上超過。却下 |
| **見直しトリガー** | **続き読み（offset 指定）が多発**し完了時間が伸びる → 比率を上げる（深掘りのみ 30% など）。**block 到達**や読取枠超過が出る → 下げる／合計予算を絞る |
| **指標** | 1 ファイルあたりの読取回数（続き読み回数）、1 ターンの読取トークン合計、block 到達率 |
| **影響** | T01, T13, K01, X09 |

<a id="dr-10"></a>
### DR-10 履歴保持（直近ターン・要約）を可変にする

| 項目 | 内容 |
|------|------|
| **決定** | `keepRecentUserTurns`：コ 2／3／4、文 3／4／6。`compactKeepRecentUserTurns`：コ 1／1／2、文 1／2／3。`summaryPurposeCount`：コ 3／5／8、文 5／8／10 |
| **根拠** | ① コーディング標準は**現行維持**［現］。② 軽快は短 ctx に合わせて保持を減らす。③ 深掘りと文章は**文脈の一貫**が価値（10 §3.3：長文一貫・用語統一）なので長く保持 **[推]**。④ 履歴保持は「根拠の厚さ」軸に直結し、ctx の数%を超えて効く（DR-02 を満たす） |
| **検討した代替** | **固定**：文章で一貫性が崩れる懸念。却下 |
| **見直しトリガー** | 文章深掘りで**用語・設定が崩れる** → 保持を増やす。**圧縮が頻発**し ctx を圧迫 → 保持を減らす |
| **指標** | 圧縮発動回数、文章の用語統一評価、同一依頼の再説明回数 |
| **影響** | C04, C05, C07 |

<a id="dr-11"></a>
### DR-11 `temperature`／`charsPerToken` は系統固定

| 項目 | 内容 |
|------|------|
| **決定** | `temperature`：コーディング **0.2**（現行維持）、文章 **0.7**。`charsPerToken`：コーディング **2**（現行維持）、文章 **1.5**。いずれも**パターンでは変えない**（S 区分） |
| **根拠** | ① パターンの軸は**待ち時間／失敗への粘り／根拠の厚さ**。temperature は**文体・創造性**で別軸（「深掘り」で上げても深くはならない）。② コーディングの 0.2 は、揺れを上げると「消す行（-）が現状とずれる」ためという現行説明に基づく［現］。③ 文章 0.7 は一般的な文章生成の目安で **[推]**。④ 日本語は 1 文字あたりのトークンがコードより多いため、見積を**保守的**にする 1.5 **[推]**（P3） |
| **検討した代替** | **temperature をパターンで変える（0.5／0.7／0.8）**：当初案。軸が違うため却下。文体を変えたくなったら別の「文体」設定として切り出す |
| **見直しトリガー** | 文章の**使用見込みと実トークンの乖離**が大きい（案: ±20%）→ 係数更新。文章で単調／暴走 → temperature 調整 |
| **指標** | 見積トークン対 `llama-server` 実トークン、文章の評価 |
| **影響** | G01, G04 |

<a id="dr-13"></a>
### DR-13 モデル・自動実行・read_file 許可はパターンから独立

| 項目 | 内容 |
|------|------|
| **決定** | GGUF の選択、**Agent 自動実行 ON/OFF**、自動実行時の **read_file 許可**は、パターンに含めない |
| **根拠** | ① ユーザー決定（2026-11-20）。② モデルは**ユーザー資産**（GGUF 非同梱。ライセンスは利用者責任）で、パターンと結びつけると導線が破綻する。③ 自動実行は**適用の安全性**（誤適用）に関わる。パターン切替で意図せず自動適用が ON になる事故を避ける。④ パターン選択時は**目安の表示のみ**（例: 「このパターンは 12B 前後向け」）で縛らない |
| **検討した代替** | **自動実行をパターンに含める**：深掘りで ON など。誤適用リスクが高い。却下 |
| **見直しトリガー** | 「パターンとモデルの不整合で失敗する」問い合わせが多い → 目安警告の強化（紐づけではなく通知） |
| **影響** | X04〜X06 |

<a id="dr-14"></a>
### DR-14 `web_mode`／`local_rag_depth` のパターン割当

| 項目 | 内容 |
|------|------|
| **決定** | `web_mode`：コ 軽快 `fail_only`／標準 `docs`／深掘り `docs+community`、文 `off`／`on_demand`／`docs+community`。`local_rag_depth`：コ 直近のみ／WS 索引＋メモ／＋ログ・上流メモ、文 キーワード／WS・メモ／厚め |
| **根拠** | ① 09 の方針：**検索範囲を狭く・版固定・失敗時だけ・引用付き**。無制限の常時検索はしない。② 軽快は速度優先で外向きを最小（失敗時のみ）。標準は Docs（P0）＋失敗駆動（P1）。③ **公式以外（community）は深掘りのみ**：ノイズ・機微の観点から条件付き（ユーザー要望「公式以外も整備」＋リスク抑制）。④ ローカル RAG は機微情報の強みを活かす柱（11）で、深さを根拠の厚さ軸に割り当てる |
| **注意** | `web_mode`／`local_rag_depth` は**未実装**。初期は既存の Docs 取得 ON/OFF に写像する。09 の手法 B／C、11 の R1〜R4 も未実装のため、初期は割当が**設計意図**である |
| **検討した代替** | **全パターンで同一**：根拠の厚さ軸を表現できない。却下 |
| **見直しトリガー** | 非公式チャネルの**ノイズで品質低下**／機微漏えいの懸念 → 許可リスト厳格化、または深掘りでも既定 OFF。Docs 取得の失敗・遅延が体感を損なう → 軽快でも既定 OFF |
| **指標** | 参照採用率、参照による修正成功率の差、外向きクエリ件数、ネット失敗時の継続率 |
| **影響** | X07, X08 |

<a id="dr-15"></a>
### DR-15 系統（文章／コーディング）の判定と適用タイミング

| 項目 | 内容 |
|------|------|
| **決定** | ① **系統は開いているワークスペースで決める**：`index.kind == novel` → 文章、それ以外 → コーディング。② **パターン選択は常に保存**し、選んだ系統が現在の系統と同じときだけ即展開する（違う系統は次にその系統のワークスペースを開いたとき）。③ **初回起動（適用済み系統が未記録）はコーディング標準を展開**してからサイドカーを起動する（再起動を 1 回で済ませる）。④ **系統が切り替わったら展開し直す**（ハーネス全値＋ctx＋thinking）。⑤ 展開は**ハーネスを丸ごと置換**する。ctx／thinking は llama.cpp のときだけ変更し、**値が変わるときだけ** `llama-server` を再起動する。Strata はハーネスのみ。⑥ 生成中・サーバ切替中は展開せず、適用済み系統を更新しない（次の機会に再試行）。⑦ S11 や詳細欄での手動変更は、次にパターンを選び直す／系統が切り替わるまで残る |
| **根拠** | ① 利用者は「小説かコードか」を別途選ばない。既にワークスペース種別が判定済みで、追加操作なしに系統が決まる（ユーザー要望「ハーネスを細かく設定させない」）。② ctx 変更は再起動（数秒〜）を伴うため、**差分があるときだけ**行う。起動時の初回展開をサイドカー前に置けば二重起動を避けられる。③ 手動変更を潰さないのは、既存ユーザー（S11 で ctx を設定済み）の挙動を急に変えないため。ただし系統切替時は意図的に上書きする（系統ごとに最適値が異なるため） |
| **検討した代替** | **常にチャット単位で系統を選ばせる**：選択負担が増える。却下。**起動ごとに必ず展開**：手動調整が毎回消える。却下。**ctx 変更は常に再起動**：不要な待ちが出る。却下 |
| **見直しトリガー** | 小説と一般文書など**判定が合わないワークスペース**が出る → 系統の手動上書き（ワークスペース単位）を追加。パターン切替の**再起動待ちが不満** → ctx は次回起動時に反映する方式へ。手動変更が**黙って消える苦情** → 系統切替時の確認表示 |
| **指標** | 系統切替時の再起動回数、パターン展開に失敗した率、展開後に ctx を手動で戻した率 |
| **影響** | `CodingPatternProfiles.systemFor`、`_applyPatternProfile`、`_onStarted`、`_onOpenWorkspace`、設定ダイアログ |
