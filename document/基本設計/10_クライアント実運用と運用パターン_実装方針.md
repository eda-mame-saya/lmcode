本ドキュメントは、**クライアント PC 上で実運用できること**を第一評価軸にしたプロダクト再整備と、ユーザー向け **運用パターン（軽快／標準／深掘り）** の実装方針である。

---

## 1. 狙い（一文）

**10B〜26B 級を現実速度で回し、生成失敗・幻覚・鮮度不足を「ツール＋検証＋整理」で潰す。**  
大規模ローカル LLM のロマン（長時間自律・超長 ctx・思考頼み）は追わず、失敗ストレスの低減を優先する。

---

## 2. プロダクト方針の固定

| 項目 | 方針 |
|------|------|
| モデル帯 | **10B〜26B** を実運用想定。速度優先では Gemma 4 系など 〜12B を第一候補に文書化 |
| 品質の取り方 | モデル拡大より **失敗削減パイプライン**（検証・再試行・根拠取得・ガード） |
| 大規模連携 | Strata 等は **限定的／非フォーカス**（実験・詳細へ退避） |
| 比較対象 | クラウド Agent との性能競争ではなく、**端末完結・機微情報・体感速度・失敗の少なさ** |
| 価値領域 | コーディング Agent ＋ **上流整理・エラーログ整理**（ローカルの強み）＋ Web／ローカル RAG |

### 2.1 含まない／制限

* クラウド LLM を生成の正にすること
* 巨大 GGUF／超長 ctx／思考 ON を「推奨」にすること
* 無制限 Web 検索の常時 Agent
* ユーザーにハーネス数値を細かく弄らせることを標準導線にすること

---

## 3. 運用パターン（軽快／標準／深掘り）

### 3.1 原則

| 原則 | 内容 |
|------|------|
| 二系統 | **文章用**と**コーディング用**を別プロファイル（ID も分ける） |
| 名称 | **軽快／標準／深掘り**（既定は各系統とも **標準**） |
| モデル | **切り離し**。GGUF 選択は独立（目安表示のみ） |
| 自動実行 | **切り離し**。S16 の Agent 自動実行トグルは独立 |
| 表に出す | 文章パターン・コーディングパターン・モデル・自動実行・（任意）Web 全体 OFF |
| 表に出さない | ctx／thinking／温度／step 上限／再試行／RAG 深さ等（パターンが束ねる） |
| 上級者 | 現行ハーネス個別編集は **詳細／開発者向け** に退避。標準導線に置かない |

```text
文章パターン         [ 標準 ▼ ]
コーディングパターン [ 標準 ▼ ]
モデル               [ … ▼ ]        ← 独立
Agent自動実行        [ ON/OFF ]     ← 独立
```

### 3.2 コーディングパターン

思考（thinking）は **ループ要因**のため、コーディングでは次を固定する。

| | **軽快** | **標準（既定）** | **深掘り** |
|--|----------|------------------|------------|
| 向き | 小さな修正・質問・ログ要約 | 日常の実装・バグ修正 | 横断調査・根拠厚めの修正 |
| thinking | **OFF** | **OFF** | **OFF（原則）** ※思考頼みにしない |
| ctx（内部） | 短 | 中 | 中〜長（256k は非推奨） |
| Agent | 短い・tool 少 | 標準上限・検証あり | 読取／参照予算増。ターン上限は上げすぎない |
| 再試行・検証の厚さ | 薄め | 現行相当を基準に再設計 | 失敗時の根拠取得を厚く |
| Web／RAG | 弱／ローカル中心 | Docs＋失敗時 | Docs＋失敗＋条件付き非公式 |
| やらないこと | 長い自律 | thinking ON | thinking で品質を稼ぐこと |

**深掘り ≠ thinking ON。** 深掘りは参照と検証を厚くする。

自動実行 ON 時の「適用 → analyze → test → 失敗時再修正」は **自動実行レイヤの仕様**（S16）。  
パターンは、その中の **予算・再試行の厚さ・失敗時 Web／RAG** を変える。

### 3.3 文章パターン

パッチ検証ループが主でない用途（ドキュメント作成／修正・要約・小説 WS 等）。

| | **軽快** | **標準** | **深掘り** |
|--|----------|----------|------------|
| 向き | 短文・言い換え | 通常の文書作成・修正 | 長文一貫・構成・用語統一 |
| thinking | OFF | OFF | **許容（深掘りのみ）** |
| ctx | 短〜中 | 中 | 長め |
| RAG | 直近／キーワード程度 | WS／メモ索引 | 厚めのローカル参照 |
| Web | 基本オフ | 必要時のみ | 調査寄り（コーディング深掘りより弱くてよい） |
| 自動検証 | 接続しない | 接続しない | 接続しない |

### 3.4 内部マップ（実装イメージ）

```text
profile_id:
  writing.light | writing.standard | writing.deep
  coding.light  | coding.standard  | coding.deep

→ llama: ctx, thinking 方針
→ agent: max_steps, read/clip 予算, retry, verify 関連の差
→ retrieve: local_rag_depth, web_mode (off | fail_only | docs | docs+community)
→ 束ねない: model GGUF, auto_execute ON/OFF, Strata/ポート等
```

数値の**初期採用値**は **[13_ハーネス数値棚卸し_パターン分け一覧.md](./13_ハーネス数値棚卸し_パターン分け一覧.md)**（52 項目・区分 A／D／S／F／M）。**根拠・前提・見直しトリガーは [14_ハーネス初期値の根拠_決定記録.md](./14_ハーネス初期値の根拠_決定記録.md)**。パターンで変えるのは約 10 項目のみ。実測後の確定値は 13 に反映し、14 §6 に変更を記録する。  
現状の個別つまみ UI（S16 歯車のハーネス）は、パターン導入後に詳細へ移す。

## 4. Agent 振る舞いの可視化（必須）

ユーザーが細かい定数を見なくても、**自動実行時に何が起きるか**をイメージできること。

### 4.1 代表経路（コーディング・自動実行 ON・Flutter）

**経路1 — 一発成功**

```text
指示送信 →（読取・計画）→ Update/Add 生成 → 自動適用
  → flutter analyze OK → flutter test OK → 完了
```

**経路2 — 検証失敗→自動再修正**

```text
指示送信 → 生成 → 自動適用
  → analyze/test 失敗
  →（パターンに応じ）失敗要約 ± 根拠取得
  → 再生成 → 再適用 → …（最大 N セット）
  → 成功 / 打ち切り＋失敗要約
```

**経路3 — 自動実行 OFF（対比）**

```text
指示送信 → 生成 → ユーザーが適用／却下
  → 自動では test まで行かない（明示の「テストを実行」等は別）
```

**経路4 — 検証スキップ系**（ドキュメント作成など、既存仕様で analyze/test しないもの）

```text
指示送信 → Add 文書 →（ON なら自動作成）→ 検証ループなし → 完了
```

### 4.2 出し方

| 場所 | 内容 | 状態 |
|------|------|------|
| 設計正本 | 上記経路を本ドキュメントで固定 | 本節で設計済 |
| S16 チャット上部の「Agent の動き」ポップアップ（ヒストリーの左隣） | いまの＋・入力・自動実行・ワークスペース種別・パターンから、手順・失敗時ループ・終わり方を動的に表示。冒頭に「ファイル変更／analyze・test／失敗時の自動修正」の 3 結論 | **実装済**（`CodingAgentFlow`） |
| パターン説明 | 軽快／標準／深掘りで N・Web・読取の差のみ注記 | 未着手 |
| 実行中ステータス | 今どこか（生成／適用／analyze／test／再修正 k/N） | **実装済**（フッター左の段階表示） |
| 打ち切り時の次の手段 | 検証が止まった理由ごとに「次にやること」を会話へ追記（最初のエラー行＋手順） | **実装済**（`codingVerifyNextStepsText`） |
| Agent カード一覧 | Patch／作成カードが積み上がると見づらいため、「カード一覧」折りたたみにまとめる。既定は閉じ、**カードが作られたら自動展開** | **未着手**（12 V6） |

文言の約束: 「自動実行＝すぐテスト」ではなく、**適用 →（Flutter なら）analyze → test → 失敗時のみ再ループ**。
