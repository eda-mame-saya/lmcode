# Web 参照による Agent 補完 — 新規機能実装方針

最終更新: 2026-11-20

本ドキュメントは、**ローカル LLM の弱みをネット参照で補う Agent 機能**の実装方針である。  
詳細な tool 契約・UI 文言は導入時に詳細設計（IF／S16）へ落とす。

---

## 1. 背景

| これまでの前提 | 現方針 |
|----------------|--------|
| オフライン完結を強く意識したローカル LLM アプリ | **オフラインは前提にしない** |
| 生成も参照も端末内で完結 | 生成の正はローカルのまま、**参照は Web／公開データを許容** |

プロダクトの正体は **ローカル LLM 中核のコーディングアシスト**である。  
クラウド LLM へ生成を委譲することはしない。ネットは **根拠の取得と検証**に使う。

ローカル LLM（特に 14B 級前後）の典型的な弱み:

* 学習カットオフによる **古い／存在しない API**
* エラーメッセージに対する **デバッグ経験の不足**
* 「それっぽい」が残る **幻覚**（存在しないメソッド・引数）

---

## 2. 目的・非目的

### 2.1 目的

1. Agent が **版付きの公式情報・成功事例・レジストリ事実**を取得し、ローカル LLM の生成品質を上げる。  
2. 既存の S16 Agent ループ（読取・パッチ・Flutter 自動検証）に、**条件付きの外向き参照**を接続する。  
3. セキュリティ方針（ソース全文の常時送信禁止・最小限クエリ）を守ったまま導入する。

### 2.2 非目的（当面）

| 含まない | 理由 |
|----------|------|
| クラウド LLM を生成エンジンにする | プロダクト方針に反する |
| 無制限の汎用 web_search を常時実行 | 小〜中規模モデルではノイズ・ctx 圧迫で逆効果になりやすい |
| ソース全文のクラウド常時同期／自前バックエンド必須化 | データ正本は端末 |
| オフライン必須の保証 | 製品要件としない（ネットなしでも編集・ローカル LLM は可能な範囲で動く） |

## 3. 採用候補（効果の高い 3 手法）

調査時点で、コーディング Agent × ネット接続において効きやすいのは次の 3 系統である。  
いずれも「生成をクラウドに渡す」のではなく **根拠を足す／検証する**。

### 3.1 手法 A — バージョン固定の公式ドキュメント取得（Docs RAG）

| 項目 | 内容 |
|------|------|
| 概要 | 依存の実バージョン（例: `pubspec.lock`）を見て、該当ライブラリの公式ドキュメント／コード例を取得し、生成直前のコンテキストに渡す |
| 補う弱み | 知識カットオフ、API 幻覚 |
| 効果 | 新規実装・ライブラリ API 利用で **常時**効きやすい。業界でも「モデル拡大より retrieval」が正面の解とされる |
| 参考形 | Context7 型（ライブラリ解決 → 版付き docs クエリ）、公式 docs の crawl→chunk→retrieve |
| LMCode 親和性 | Flutter 第一ターゲットなら `flutter`／Dart SDK／主要 plugin の版付き docs が最優先。送信はライブラリ名・版・質問程度に抑えやすい |

### 3.2 手法 B — 失敗駆動の事例検索（エラー → SO／GitHub Issue・PR）

| 項目 | 内容 |
|------|------|
| 概要 | `analyze`／`test`／コンパイル失敗時にエラー文を正規化（パス・行番号除去）して検索し、採用回答・クローズ済み Issue・マージ済み PR の diff を取得して再修正する |
| 補う弱み | 未知エラーでの自己修正の弱さ |
| 効果 | 成功事例のコード／実 diff を渡すと、ゼロから推論するより修正精度が上がりやすい。Copilot Coding Agent 等も「珍しいエラー／カットオフ以降の変化」向けに web search を追加 |
| LMCode 親和性 | 既存の Flutter 自動検証（analyze→test、最大 3 セット）の **失敗時だけ**起動する条件付きネットにしやすい |

### 3.3 手法 C — レジストリ／公開ソースによる事実の確定（API 面グラウンディング）

| 項目 | 内容 |
|------|------|
| 概要 | 書く前・書いた後に pub.dev 等のレジストリやタグ付き公開ソースから、版・changelog・公開 API／シグネチャを確定情報として取る。発展形では生成コードと突き合わせて存在しないメソッドを弾き、再生成する |
| 補う弱み | 幻覚の残留（検索 RAG だけでは SEO／古い投稿が混ざる） |
| 効果 | **版がはっきりした一次情報**で嘘を削ぐ。小モデルでは「ツール多用の長いエージェント」より retrieve→生成→ルール検証の短いループが有利な報告もある |
| LMCode 親和性 | まず「この版でその API はあるか」の確認だけでも手法 A と相性が良い |

### 3.4 比較と導入優先

| 優先 | 手法 | 効果の出方 | 実装の重さ |
|------|------|------------|------------|
| **P0** | A Docs RAG | 日常のコーディング品質 | 中 |
| **P1** | B 失敗駆動検索 | 自動検証失敗時 | 中（既存ループに接続） |
| **P2** | C レジストリ／シグネチャ検証 | 生成前後のガード | 小→大（段階可） |

**推奨順:** A → B → C。  
汎用 web_search 単体を最初の正としない。検索範囲を狭く・版を固定・失敗時だけ・引用付き、を原則とする。

運用パターン（軽快／標準／深掘り）導入後は、参照の強さを `web_mode`（off／fail_only／docs／docs+community）としてパターンにマップする（[10](./10_クライアント実運用と運用パターン_実装方針.md)）。公式以外（community）は深掘り寄りの条件付きとする。

## 4. Agent 振る舞い方針

```text
ユーザー指示
  →（任意・P0）依存版を解決し公式 docs／例を取得
  → ローカル LLM で計画・読取・パッチ生成（既存）
  →（任意・P2）公開 API 面と突合・矛盾なら再生成
  → 適用／自動実行（既存）
  → Flutter 等で analyze／test（既存）
  → 失敗時（P1）エラー正規化 → 事例検索 → 根拠付き再修正
  → 成功 or 上限
```

| ルール | 内容 |
|--------|------|
| 生成の正 | 常に localhost `llama-server` |
| 参照の位置づけ | LLM への入力補強。生成エンジンの代替ではない |
| 起動条件 | 常時フル検索しない。タスク種別・依存利用・検証失敗など **必要なときだけ** |
| 失敗時 | Web 参照失敗はローカルのみで継続（ベストエフォート）。Agent 全体を落とさない |
| UI | 「オフライン動作」固定表示は使わない。ローカル LLM である旨＋参照中などの進行文言（S16 フッター方針に追随） |

## 5. セキュリティ・プライバシー（守る境界）

詳細は [06_セキュリティプライバシー.md](./06_セキュリティプライバシー.md)。本機能で特に固定する点:

| よい | いけない |
|------|----------|
| ライブラリ名、版、公開 URL、エラー要約（パス除去後）、パッケージメタ | ソース全文・秘密・社内限定パスの無制限送信 |
| 取得結果の要約を会話に残す（必要最小） | Drive 連携やソースのクラウド常時同期 |
| 参照用キーは端末ローカル保管（導入時） | キーや秘密をログ・共有に出す |

外向きは HTTPS。サイドカー LLM は `127.0.0.1` のまま。

## 6. 実装フェーズ（案）

| 段階 | 内容 | 完了の目安 |
|------|------|------------|
| **F0 方針固定** | 本ドキュメント・基本設計（00／01／04／06）との整合 | 済（2026-11-19） |
| **F1 P0 Docs** | Agent tool `fetch_library_docs`。ローカル依存（package_config／node_modules 等）優先、不足時のみ pub.dev／npm／PyPI から版付き README 等。S16 設定で ON/OFF（既定 ON）。引用 URL を tool 結果に含める | **初版実装済（2026-11-19）** |
| **F2 P1 失敗駆動** | 自動検証失敗時のみ事例検索→再修正。エラー正規化必須 | 既知エラー系の自動修復率が上がる |
| **F3 P2 事実確定** | pub.dev 等のメタ取得。後続でシグネチャ突合 | 存在しない API の再提案が減る |
| **F4 IF／UI 定着** | `詳細設計/IF/` に Web 参照 IF、S11 に ON／OFF・キー、S16 進行文言 | 設計と実装が一致 |

数値目標（成功率・レイテンシ）は [04_非機能制約OS差分.md](./04_非機能制約OS差分.md) の N12 等で後追記。

## 7. 構成上の置き場

| 層 | 方針 |
|----|------|
| UI | S16 Agent（進行表示）。設定は S11 に「Web 参照を使う」等（導入時） |
| ドメイン | coding_assist の tool として参照取得を追加。既存 read／search／patch と並列 |
| 通信 | アプリまたは薄いアダプタから HTTPS。自前サーバーは置かない |
| キャッシュ | 端末ローカル（TTL）。再取得削減とオフライン時のベストエフォート用（詳細はデータ設計に追記） |

論理構成の位置づけは [01_システム構成.md](./01_システム構成.md) の「外部参照（任意）」。
